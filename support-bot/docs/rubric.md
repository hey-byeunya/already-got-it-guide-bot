# 실험 — 다섯 세팅, 225번

```bash
node scripts/embed-docs-browser-path.mjs --prefix --queries data/eval-queries.json
node scripts/run_rubric.ts --setting S0 --runs 3      # S0~S4
node scripts/summarize_rubric.ts S0 S1 S2 S3 S4
```

평가 세트 15개(`data/eval-queries.json`)를 세팅마다 **세 번씩** 돌렸습니다. 답변 원문 **225건**은 [`data/rubric/`](../data/rubric)에 있습니다.

## 왜 세 번씩 돌렸나

같은 질문에 답도 판정도 매번 달라집니다. 한 번 돌린 결과를 비교하면 달라진 게 바꾼 것 때문인지 그냥 매번 다른 것인지 알 수 없습니다. 세팅마다 세 번 돌려 **흔들림 폭을 먼저 재고, 그 폭보다 큰 차이만 변화로 읽었습니다.**

## 무엇을 누가 쟀나

**대부분을 프로그램이 잽니다.** dev-bot 은 지표 대부분을 판정 모델에 기대었다가, 그 판정 자체가 0.74밖에 맞지 않아 나머지를 읽을 수 없었습니다.

## 세팅

| 세팅 | 바꾼 것 |
|---|---|
| **S0** | — (기준 행) 고객센터 답변 형식 지시 있음 |
| **S1** | 고객센터 답변 형식 지시를 뺀다 |
| **S2** | 근거 개수를 10+5 → 5+3 으로 줄인다 |
| **S3** | 인용 요구를 프롬프트 맨 끝(질문 뒤)으로 옮긴다 |
| **S4** | S1 에서 **답을 만드는 모델만** `qwen3.5:2b` → `qwen2.5:3b` |

S4 는 판정 모델을 바꾸지 않았습니다. **재는 자를 함께 바꾸면 무엇이 달라졌는지 읽을 수 없습니다.**

## 실험 1 — 형식을 지시했더니 형식이 더 나빠졌다 (채택)

**「결론을 첫 줄에, 화면에서 누를 순서를 번호 목록으로」라고 시킨 쪽(S0)이 절차형 0/5 였고, 그 지시를 뺀 쪽(S1)이 1/5 였습니다.** 흔들림 폭이 0 이라 우연이 아닙니다. 네 지표에서 함께 좋아졌습니다.

프롬프트를 보면 이유가 보입니다 — 근거 15개에 5,023자, 그 앞에 지시가 14줄입니다. **2B 모델에게 그만큼 주면 지시를 늘릴수록 지시받은 것까지 못 합니다.**

`dev-bot` 이 「지시문으로 시킨 것은 실패했고 프로그램으로 옮긴 것만 성공했다」를 여섯 번 확인했습니다. 여기 보탤 것은 **지시가 실패하는 데 그치지 않고 다른 것까지 망가뜨린다**는 점입니다.

→ **채택.** `buildPrompt` 의 기본값을 형식 지시를 넣지 않는 쪽으로 바꿨습니다.

## 실험 2 — 근거를 줄여도 인용은 나아지지 않았다 (되돌림)

근거 15개를 8개로 줄이면 모델이 어느 것을 쓸지 잘 고를 것이라고 봤습니다. **기대 도움말 인용 비율이 0.67 로 그대로였습니다.** 범위 밖 거절만 좋아졌는데 그건 S1 도 같은 크기로 좋아졌습니다.

**원인이 근거 개수가 아니라는 뜻입니다.** → 되돌림. 10+5 를 그대로 씁니다.

## 실험 3 — 인용 요구의 위치는 아무것도 바꾸지 않았다 (되돌림)

전부 흔들림 안이었습니다. → 되돌림.

## 실험 4 — 모델을 키우면 답은 좋아지고 인용은 무너진다 (되돌림, 그러나 가장 중요한 결과)

S1 이 채택 후보로 올라온 뒤에도 답변 원문은 여전히 고객에게 낼 수 없었습니다. 남은 실패가 **문구 때문인지 모델 때문인지** 가르려고, S1 에서 답을 만드는 모델만 `qwen2.5:3b` 로 바꿨습니다.

| | S1 (2B) | S4 (3B) |
|---|---|---|
| 출처 인용 (11 중) | **11.0** | **1.7** |
| 기대 도움말 인용 | **0.79** | **0.12** |
| 절차형 (5 중) | 1.0 | **2.0** |

같은 질문(C01 「위시에 담아둔 걸 샀는데 어떻게 옮겨요?」)의 답을 나란히 놓으면 분명합니다.

> **S1 (2B)** — "상세한 설명은 [1], 하지만 2 의 문구로 이어집니다. 따라서 다음과 같이 안내할 수 있습니다. **"…라고 답변합니다."**"
>
> **S4 (3B)** — "위시에 담아 두신 물건을 실제로 사셨다면, **위시 목록**을 엽으시고, 해당 카드를 선택해주세요. 그 카드의 **「샀어요 · 있템으로」** 버튼을 누르시면 됩니다. 옮기가 완료되면 위시 카드가 사라지고, 물건이 있템 목록에 나타나게 됩니다."

2B 는 「이렇게 답변합니다」라고 메타로 말하고, 3B 는 도움말 그대로 정확하게 안내합니다. C08(「유통기한 알림이 오나요?」)에서는 3B 가 이렇게 답했습니다.

> "[1] 유통기한 알림은 오지 않습니다. 사용기한이 임박한 물건을 목록 화면에 배지로 표시만 해주며, 푸시 알림이나 메일 알림도 보내지 않습니다."

**낼 수 있는 고객센터 답변입니다.** 그런데 3B 는 11문항 중 1.7개만 인용합니다. 근거를 보여 주는 것이 이 챗봇의 목적인데, 그것을 잃습니다.

→ **이번에는 되돌림.** 답변이 좋아도 근거를 가리키지 않으면 「참고한 도움말」이 비고, 그러면 이 제품이 약속한 것이 사라집니다.

**다만 이것이 다음 회차의 출발점입니다.** 답변 품질과 인용이 서로 다른 모델에 갈려 있다는 것을 알았습니다. 다음에 잴 것은 「3B 로 답을 만들되 인용을 어떻게 붙일 것인가」입니다 — 그리고 지금까지의 결론대로라면, 그 답은 **모델에게 더 세게 부탁하는 것이 아닐 가능성이 높습니다.**

## 채택하지 못한 것을 채택한 척하지 않았다

**다섯 세팅 중 어느 것도 수용 기준을 통과하지 못했습니다.** 가장 나은 S1 도 절차형 1.0/5, 범위 밖 거절 1.3/2 입니다. S1 을 채택한 것은 **기준을 넘겨서가 아니라 기준 행보다 나아서**입니다. 통과로 적지 않았습니다.
