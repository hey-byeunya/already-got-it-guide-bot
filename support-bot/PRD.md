# 이미 있어 고객센터 챗봇 — PRD

> **상태: 초안 (구현 시작 전).** 이 문서를 먼저 쓰고, 이 문서를 기준으로 만든다.
> 아직 정하지 못한 것은 `[결정 필요]`로 남긴다. **빈칸을 남긴 채 구현을 시작하면, 나중의 코드 선택이 제품 약속을 대신하게 된다.**
> 같은 저장소의 [`dev-bot/`](../dev-bot)은 같은 서비스를 다루는 **개발자용** 챗봇이다. 무엇을 이어받고 무엇을 바꿨는지는 9절에 있다.

## 0. 이 문서로 판단할 것

처음 보는 사람이 이 문서를 읽고 **무엇을 물을 수 있고 무엇을 기대하면 안 되는지** 알 수 있어야 한다.

한 줄로 답하면 — **"이미 있어" 앱을 쓰다 막혔을 때 무엇을 어떻게 누르면 되는지는 물을 수 있고, 내 계정 안에 무엇이 들어 있는지는 물을 수 없다.**

---

## 1. 문제 정의 — 어떤 질문에, 어떤 근거로 답하는가

### 1-1. 고객이 실제로 막히는 자리

"이미 있어"는 개인용 재고 관리 앱이다. 쓰다 막히면 지금은 **물어볼 곳이 없다.** 앱 안에 도움말도 문의 창구도 없고, 공개된 문서는 개발자를 위해 쓰인 것뿐이다. 막힌 사람은 화면을 이리저리 눌러 보다 포기한다.

실제로 막히는 자리 다섯 곳:

| # | 고객이 겪는 일 | 고객이 던지는 질문 |
|---|---|---|
| 1 | 위시에 담아둔 걸 샀는데, 목록을 옮기는 방법을 못 찾는다 | "산 물건은 어떻게 있템으로 옮겨요?" |
| 2 | 등록 폼에서 카테고리를 비웠더니 저장이 안 된다 | "카테고리는 꼭 넣어야 하나요?" |
| 3 | 다 쓴 물건이 목록에서 사라져 없어진 줄 안다 | "다 쓴 물건은 어디로 갔나요? 되돌릴 수 있나요?" |
| 4 | 어제 본 D-day 숫자와 오늘 숫자가 다르다 | "D-day가 왜 달라졌나요? 빨간 배지는 무슨 뜻이에요?" |
| 5 | 유통기한 알림이 올 줄 알고 기다린다 | "알림은 언제 오나요?" (→ **없는 기능이다**) |

5번이 특히 중요하다. **없는 기능을 없다고 말해 주는 것**이 고객센터의 일이다. 지금은 아무도 말해 주지 않아서 고객이 기다린다.

### 1-2. 어떤 근거로 답하는가

**고객이 직접 열어 읽을 수 있는 도움말 문서**에 적힌 것만 근거로 삼는다 (4절).

답할 때마다 **어느 도움말의 어느 대목을 근거로 삼았는지** 함께 보여 준다. 이것이 이 챗봇의 핵심이다 — 고객은 챗봇의 말을 믿을지 말지를 스스로 정할 수 있어야 하고, 그러려면 원문을 열 수 있어야 한다.

> **매끄러운 답과 근거 있는 답은 다르다.** dev-bot 에서 실제로 겪었다 — 매끄러운 791자 답변이 원문의 "~하지 않는다"를 "~한다"로 뒤집은 곳이 두 군데 있었고, 자동 판정은 85점을 줬다. 그래서 이 챗봇은 답변의 유창함을 근거의 증거로 쓰지 않고, 두 사실을 화면에서 **따로** 보여 준다.

## 2. 타겟 유저 — 누가 사용하는가

| 누구 | 무엇을 묻는가 | 무엇을 기대하면 안 되는가 |
|---|---|---|
| **① 앱을 쓰다 막힌 고객** (주인공) | 화면에서 무엇을 어떤 순서로 눌러야 하는지 | 내 계정 안의 데이터. 이 챗봇은 로그인하지 않는다 |
| **② 규칙에 막힌 고객** | 왜 저장이 안 되는지, 무엇이 필수인지 | "그 값은 통과합니다"라는 판정. 규칙이 적힌 문장을 보여 줄 뿐이다 (7-3) |
| **③ 이 챗봇을 검토하는 사람** | 답이 어느 도움말 어느 대목에서 나왔는지, 판정이 맞는지 | 판정 배지가 답의 정확성을 증명해 준다는 것. 판정은 답을 만든 것과 같은 2B 모델이 한다 |

**①이 주인공이라는 점이 dev-bot 과 가장 크게 다르다.** dev-bot 은 ③(검토자)을 위한 화면이었다 — 유사도 점수와 판정 배지가 전면에 있었다. 이 챗봇에서 ③을 위한 것은 **「자세히 보기」 토글 뒤로 물러난다.** 지우지는 않는다. 검토할 수 없는 챗봇은 근거를 보여 준다고 말할 자격이 없다.

**로그인한 사용자를 대상으로 삼지 않는다.** 누구인지 몰라도 답할 수 있는 것만 다룬다.

## 3. 핵심 기능 (MVP)

기능 이름만 적으면 왜 있는지 알 수 없다. **각 항목에 고객의 무슨 판단을 돕는지 붙인다.**

| # | 기능 | 고객이 무엇을 판단하게 되는가 |
|---|---|---|
| 1 | **근거 검색** — 질문을 벡터로 바꿔 도움말 조각을 하이브리드 검색 | (직접 보이지 않음. 아래 전부의 재료) |
| 2 | **출처 공개** — 답변 아래 「참고한 도움말」 카드 + 원문 열기 | 이 답을 믿을지, 원문을 열어 볼지 스스로 정한다 |
| 3 | **답변 생성** — 고객센터 형식으로 스트리밍, 중지 가능 | 답이 길어질 때 계속 기다릴지 끊을지 정한다 |
| 4 | **자동 판정** — 근거성·환각·정당한 거절을 다시 읽는다 | 답을 두 번째 시선으로 다시 읽는다 |
| 5 | **인용 계수** — 답변이 근거를 실제로 가리켰는지 **프로그램이 센다** | "출처를 밝힌 답"이라는 말을 숫자로 믿을 수 있다 |
| 6 | **호출 전 검사** — 개인 데이터·대행 요청을 모델에 보내기 전에 막는다 | 왜 답이 안 나왔는지 안다 (고장이 아니라 범위 밖) |
| 7 | **약한 근거 안내** — 딱 맞는 도움말이 없으면 미리 알린다 | 근거가 약한 답을 평소와 같은 자신감으로 읽지 않는다 |
| 8 | **사람 피드백** — 도움됐어요 / 아니에요 | 자동 판정이 놓친 것을 사람이 표시한다 |
| 9 | **부정문 표시** — 근거 원문의 "~하지 않는다" 문장을 짚어 준다 | 답이 원문을 뒤집었는지 대조할 자리를 안다 |

### 3-1. 답변 형식 — 고객센터 상담 답변처럼

답변은 **네 덩어리**로 나온다. 앞의 셋은 모델이 쓰고, **마지막 하나는 프로그램이 붙인다.**

```
① 결론    산 물건은 위시 목록의 「샀어요 · 있템으로」 버튼으로 옮기실 수 있습니다. [1]
② 절차    1. [위시] 탭을 엽니다.
          2. 옮길 물건 카드에서 「샀어요 · 있템으로」를 누릅니다.
          3. 성공하면 카드가 사라지고 있템 목록에 나타납니다. [1]
③ 주의    위시에는 수량 개념이 없어 옮겨진 있템의 수량은 항상 1로 들어갑니다. [2]
④ 참고    ┌ [1] 위시리스트 · 샀을 때 있템으로 옮기기   [원문 열기]
   (프로그램)└ [2] 위시리스트 · 옮길 때 값이 어떻게 넘어가나요  [원문 열기]
```

**본문에 내부 문서 ID(`HELP-WISH-02`)를 쓰지 않는다.** 고객이 읽을 답변에 내부 식별자가 있으면 그것 자체가 고객센터답지 않다. 대신 `[1]` `[2]` 번호를 쓰고, 번호와 도움말 이름을 잇는 ④는 **모델이 아니라 프로그램이 만든다.** 모델이 지어낼 수 없는 자리로 옮긴 것이다.

### 3-2. 인용 여부는 모델에게 묻지 않는다

**dev-bot 이 남긴 가장 큰 숙제를 여기서 갚는다.** 그쪽은 "답변에 출처 표시가 있는가"를 판정 모델에게 물었고, 측정한 실패 108건 중 **42건이 그 판정의 실패**였다. 형식을 정확히 맞춰도 오히려 더 자주 틀렸다.

글자를 찾으면 끝나는 일이다. 이 챗봇은 프로그램이 센다.

| 세는 것 | 방법 |
|---|---|
| 인용했는가 (`cited`) | 본문에서 `[숫자]`를 찾는다 |
| 지어낸 인용인가 | 근거가 5개인데 `[7]`이 있으면 범위 밖으로 센다 |
| 내부 ID가 새어 나왔는가 | 본문에 `HELP-`가 있으면 실패로 센다 |
| 절차형으로 답했는가 | 번호 목록과 화면 이름이 있는가 |

자동 판정(LLM-as-a-Judge)에는 **`grounded`·`noHalluc`·`refusal` 만 남긴다.** 뜻을 읽어야 하는 것만 모델에게 맡기고, 셀 수 있는 것은 프로그램이 맡는다.

## 4. 근거 자료 계획

### 4-1. 무엇을 자료로 삼는가

**`already-got-it` 저장소에 고객용 도움말 문서 7개를 새로 작성해 공개하고, 그것을 자료로 삼는다.**

기존 공개 문서(`PRD.md`·`docs/rules/*.md`·`supabase/migration.sql`)를 그대로 쓰지 않는 이유는 하나다 — **고객이 열었을 때 읽을 수 있어야 하기 때문이다.** 지금 그 문서들에는 `mark_wishlist_purchased` RPC 이름과 `check (quantity >= 1)` 같은 SQL 제약이 들어 있다. 말투만 고객센터풍으로 바꿔도 출처를 여는 순간 고객은 자기가 읽을 수 없는 문서를 만난다. 그러면 출처를 보여 주는 의미가 사라진다.

| 파일 (`docs/help/`) | 담을 것 | 답할 수 있게 되는 질문 |
|---|---|---|
| `getting-started.md` | 회원가입(닉네임 2~20자·약관 동의), 로그인, 비밀번호 재설정, 로그아웃하면 남는 것 | "닉네임 몇 자까지예요?" "비밀번호를 잊었어요" |
| `register-item.md` | 있템 등록 — 필수/선택 항목, 카테고리가 필수인 이유, 수량 규칙, 상태 3종 | "카테고리 꼭 넣어야 해요?" "수량 0으로 되나요?" |
| `wishlist.md` | 위시 담기 → 「샀어요 · 있템으로」로 옮기기, 옮길 때 값이 넘어가는 방식 | "산 물건 어떻게 옮겨요?" "카테고리 없어도 옮겨지나요?" |
| `used-items.md` | 쓴템 탭 — 다 쓴 물건이 가는 곳, 되돌리기, 「다 쓴 것도 보기」 | "다 쓴 물건 어디 있어요?" "되돌릴 수 있나요?" |
| `search-and-dday.md` | 검색·정렬, D-day 배지 4단계, 날짜가 매일 달라지는 이유 | "빨간 배지가 뭐예요?" "어제랑 숫자가 달라요" |
| `account-and-data.md` | 계정·데이터 보관 범위, 로그아웃 시 지워지는 것 | "다른 계정으로 로그인하면 이전 데이터가 보이나요?" |
| `faq.md` | 자주 묻는 질문 — **없는 기능을 명시** (알림·바코드·통계·닉네임 변경·탈퇴) | "유통기한 알림 와요?" "바코드 스캔 돼요?" |

> ⚠️ **도움말은 사람이 쓴다.** 기존 개발 문서를 근거로 하되 문장은 새로 쓰고, **어느 문장이 어느 개발 문서에서 왔는지 대조표**를 `docs/corpus.md`에 남긴다. 도움말이 원본과 어긋나면 챗봇은 정확한 근거로 틀린 답을 하게 된다 — 근거가 있다는 사실이 오히려 위험해진다.

> ⚠️ **다른 저장소에 푸시하기 전까지 출처 URL은 404다.** 초안을 만들어 확인받고, 승인 뒤 `already-got-it` 에 올린다. 그 전에는 벡터스토어를 만들지 않는다.

### 4-2. 청크 스키마와 ID 규칙

원문에서 **연속 구간을 그대로 잘라** 청크를 만든다. 요약하거나 다시 쓰지 않는다 — 고객이 출처를 열었을 때 같은 문장이 그 자리에 있어야 한다.

```json
{
  "id": "HELP-WISH-02",
  "url": "https://github.com/hey-byeunya/already-got-it/blob/main/docs/help/wishlist.md#샀을-때-있템으로-옮기기",
  "doc": "위시리스트",
  "section": "샀을 때 있템으로 옮기기",
  "text": "…원문 그대로…"
}
```

| 필드 | 뜻 | 왜 필요한가 |
|---|---|---|
| `id` | `HELP-{주제}-{두자리}` | 사람이 읽지 않는 내부 식별자. 화면에는 검토 모드에서만 보인다 |
| `url` | 앵커까지 붙은 공개 주소 | 고객이 원문을 연다 |
| `doc` | 「위시리스트」 | **화면에 보이는 이름표.** dev-bot 에는 없던 필드다 |
| `section` | 「샀을 때 있템으로 옮기기」 | 문서 어느 대목인지 |
| `text` | 원문 그대로 | 근거 모달에 전문을 띄운다 |

**주제 코드 7개**: `GET`(시작하기) · `ITEM`(있템 등록) · `WISH`(위시) · `USED`(쓴템) · `FIND`(검색·D-day) · `ACCT`(계정·데이터) · `FAQ`

**실제 26개** (목표는 18~22였다 — 10절 1번에 왜 넘겼는지 적었다). 한 청크에 한 주제, 120자 이상.

| 도움말 | 청크 | 도움말 | 청크 |
|---|---|---|---|
| 시작하기 | 4 | 찾기와 D-day | 3 |
| 있템 등록 | 4 | 계정과 내 데이터 | 3 |
| 위시리스트 | 3 | 자주 묻는 질문 | 6 |
| 쓴템 | 3 | **합계** | **26** |

`scripts/build_chunks.py` 가 매번 검사한다 — 기대한 절 제목이 아직 있는가, 각 청크가 120자 이상인가, 출처 주소가 겹치지 않는가, **그리고 앵커가 실제로 그 자리로 가는가.** 마지막 것이 중요하다: 제목을 고치면 문서는 그대로 열리는데 앵커만 죽는다. 눈으로는 보이지 않는 실패다.

### 4-3. 벡터스토어

청크를 미리 임베딩해 **정적 파일**로 배치한다 (`app/public/help-docs.json`). 서버가 없으므로 브라우저가 이 파일을 통째로 받아 메모리에서 검색한다.

- 임베딩 모델: `EmbeddingGemma-300m` (768차원), 문서/질문 접두어를 붙여 쓴다
- **문서 벡터(Node)와 질문 벡터(브라우저)는 같은 경로로 만든다** — 같은 모델 파일, 같은 wasm 실행, 같은 mean pooling, 같은 L2 정규화. 하나라도 다르면 두 벡터가 다른 공간에 놓여 코사인 점수가 뜻을 잃는다. 화면의 「임베딩 대조」로 언제든 다시 잰다
- 첫 방문에 임베딩 모델 약 195MB를 받는다 → **진행률 막대와 바이트 표시**, 받은 뒤에는 브라우저에 캐시

## 5. 화면 구성

**한 페이지짜리 앱이다.** 화면을 나누지 않는 이유는, 질문한 순간부터 답변과 근거가 한자리에 함께 보여야 하기 때문이다. 근거를 보러 다른 화면으로 가야 하면 아무도 대조하지 않는다.

대신 **두 시선**으로 나눈다. 기본은 고객 모드, 검토용은 토글 뒤에 있다.

| 영역 | 고객 모드 (기본) | 검토 모드 (토글 시 추가) |
|---|---|---|
| **인사·시작 화면** | 인사말 + 자주 묻는 질문 버튼 6개 + 사용 조건 | — |
| **연결 상태** | 「지금은 답변을 만들어 드릴 수 없습니다」 + 해결 방법 + 재시도 | Ollama 응답 원문 |
| **진행 표시** | 「도움말을 찾고 있습니다」 / 모델 내려받기 진행률 막대 | 단계 이름과 소요 |
| **답변** | 결론 → 절차 → 주의 (스트리밍, 중지 버튼) | 모델에게 보낸 프롬프트 전문 |
| **참고한 도움말** | 「위시리스트 · 샀을 때 옮기기」 카드 + 「원문 열기」 | ID · 검색 방법(vector/bm25) · 유사도 점수 |
| **근거 모달** | 도움말 원문 전체 | 부정문 표시, bm25 점수 해석 주의 |
| **판정** | 「근거 확인됨」 / 「확인이 필요합니다」 한 줄 | grounded · noHalluc · refusal 배지 + 점수 + 평어 |
| **호출 전 검사 배너** | 「이건 도와드릴 수 없습니다」 + 앱 화면 경로 | 어느 규칙이 막았는지 |
| **약한 근거 안내** | 「딱 맞는 도움말을 찾지 못했습니다」 | 최고 유사도 숫자와 기준값 |
| **피드백** | 도움됐어요 / 아니에요 | 자동 판정과 어긋나면 경고 |

**만들지 않는 화면**: 로그인, 대화 기록 보관, 설정 페이지, 상담원 연결.

### 5-1. 화면이 지켜야 할 것

- **「참고한 도움말」이 비어 있으면 그 자리에 「근거를 찾지 못했습니다」를 명시한다.** 비워 두면 고객은 근거가 있는데 표시만 안 된 것으로 읽는다.
- **판정 결과를 답변 옆에 나란히 두지 않는다.** 매끄러움과 근거는 다른 사실이므로 다른 줄에 둔다.
- **연결 실패를 「오류」로 쓰지 않는다.** 고객은 앱이 고장 났다고 읽는다.

## 6. 비목표 — 이번 범위에서 약속하지 않는 것

비목표는 목표를 줄이는 사과가 아니라, **어떤 계약을 약속하지 않는지 미리 선언하는 안전장치**다.

| 하지 않는 것 | 이유 |
|---|---|
| 로그인 · 계정 연동 | 누구인지 몰라도 답할 수 있는 것만 다룬다 |
| 개인 데이터 조회 ("내 있템 몇 개?") | 개인정보 열람은 챗봇이 단독으로 결정하지 않는다 |
| 값이 규칙에 맞는지 판정해 주기 | 판정에는 폼의 맥락이 필요하다. 규칙 문장을 보여 주는 데까지만 한다 (7-3) |
| 상태 변경 대행 (위시→있템 옮기기 등) | 되돌릴 수 없는 동작이다. 사람이 앱 화면에서 직접 누른다 |
| 계정·비밀번호 대행 | 재설정 메일 발송·약관 동의·닉네임 변경을 대신하지 않는다. 화면 경로만 안내한다 |
| 서버에서 자료 수집 | 서버가 없다. 자료는 미리 만들어 둔 파일이다 |
| 다국어 · 모바일 최적화 | 이번 범위 밖 |

> 위 셋(개인 데이터 조회 · 값 판정 · 상태 변경)은 [4강 설계 패킷](https://github.com/hey-byeunya/my-service-agent/blob/main/design-packet.md)의 도구 2·3·4다. 설계에서 이미 "챗봇이 단독으로 결정하지 않는다"고 정한 것들이다.

**앞의 셋은 프롬프트로 부탁하지 않고 프로그램이 막는다** (호출 전 검사, 3절 6번). dev-bot 에서 지시문으로 적어 두었을 때 세 번 중 한 번 새어 나갔다.

## 7. 자료 밖 질문 처리 기준

자료에 없는 질문은 **그럴듯하게 넓혀 답하지 않는다.** 범위 밖임을 밝힌 뒤 답할 수 없다고 안내한다.

> 이 기준은 **거절을 줄이려는 장치가 아니라, 고객이 답변의 경계를 이해하게 하는 약속이다.**
> 그래서 정당한 거절을 실패로 세지 않고 따로 센다. **거절이 줄어드는 것은 좋은 신호가 아니다** — 자료 밖 질문에 답을 지어내기 시작하면 거절은 줄어든다.

### 7-1. 네 경우

| 상황 | 행동 |
|---|---|
| 검색 결과가 비었다 | 도움말에 없다고 말하고 멈춘다 |
| 개인 데이터·대행을 요구한다 | **호출 전 검사가 막는다.** 범위 밖임을 밝히고 앱 화면 경로만 안내한다 |
| 근거는 있는데 약하다 (최고 유사도 0.55 미만) | 근거를 버리지 않는다. 안내를 띄우고 보수적으로 답한다 |
| 없는 기능을 묻는다 | **`faq.md`를 근거로 "없습니다"라고 답한다.** 이건 거절이 아니라 답이다 |

네 번째가 dev-bot 에 없던 것이다. "유통기한 알림 오나요?"에 "자료에 없습니다"라고 답하면 고객은 있는지 없는지 여전히 모른다. **없다는 사실을 도움말에 적어 두어, 근거를 가지고 "없습니다"라고 답할 수 있게 만든다.**

### 7-2. 판정이 실패했을 때

판정 배지 자리에 실패 표시만 남기고, **이미 만든 답변과 참고한 도움말은 지우지 않는다.** 판정은 답변을 다시 읽게 돕는 보조 장치이지, 답변이 화면에 남을 조건이 아니다.

### 7-3. 규칙을 보여 주는 것과 값을 판정하는 것의 경계

| 한다 | 하지 않는다 |
|---|---|
| 「도움말에는 수량이 1 이상이어야 한다고 되어 있습니다」 | 「그 값은 통과합니다 / 거부됩니다」 |
| 규칙 문장을 근거와 함께 보여 준다 | 도움말에 없는 조합을 미루어 판정한다 |

도움말에 그 값에 대한 문장이 없으면 **추측해서 판정하지 않고 없다고 말한다.** 판정처럼 들리는 답이 가장 위험하다 — 고객은 확인받았다고 믿고 넘어간다.

## 8. 수용 기준

### 8-1. 정량 — 고객 질문 15개를 3회씩

같은 질문에 답도 판정도 매번 달라진다. 한 번 돌린 결과로는 달라진 게 바꾼 것 때문인지 원래 흔들리는 것인지 알 수 없다. **세 번 돌려 흔들림 폭을 먼저 재고, 그 폭보다 큰 차이만 변화로 읽는다.**

| # | 기준 | 누가 재는가 | 목표 |
|---|---|---|---|
| 1 | 답해야 할 11문항 중 출처를 인용한 답 | **프로그램** | 11/11 |
| 2 | 범위를 벗어난 인용 번호 | **프로그램** | 0건 |
| 3 | 본문에 내부 ID(`HELP-`) 노출 | **프로그램** | 0건 |
| 4 | 절차를 묻는 5문항 중 절차형으로 답한 것 | **프로그램** | 5/5 |
| 5 | 범위 밖 2문항 중 거절 | 판정 모델 | 2/2 |
| 6 | 게이트 2문항 중 차단 | **프로그램** | 2/2 (흔들림 없음) |
| 7 | 잘못 막은 질문 | **프로그램** | 0건 |
| 8 | 답이 도움말에서 나온 비율 | 판정 모델 | 1.00 |

**1~4·6·7을 프로그램이 잰다.** dev-bot 에서 지표 대부분을 모델 판정에 기대었다가, 그 판정 자체가 0.74밖에 맞지 않아 나머지를 읽을 수 없었다. 셀 수 있는 것을 세는 쪽으로 옮긴다.

**목표에 못 미치면 통과로 적지 않는다.**

### 8-2. 화면 상태 6개 — 어디서 확인했는지 나눠 적는다

| # | 무엇을 확인 | 어디서 |
|---|---|---|
| 1 | 답변이 결론 → 절차 → 주의 순서로 나오는가 | 로컬 |
| 2 | 「참고한 도움말」 카드에서 원문이 열리는가 | 로컬 · **배포** |
| 3 | "제 있템 몇 개예요?"를 호출 전 검사가 막는가 | 로컬 · **배포** |
| 4 | Ollama를 끈 상태에서 안내와 재시도가 보이는가 | **배포** |
| 5 | 검토 모드 토글로 판정 배지·점수가 나타나는가 | 로컬 |
| 6 | 근거가 약할 때 안내가 뜨는가 | 로컬 |

**로컬에서 확인한 것을 배포에서 확인한 것처럼 적지 않는다.**

### 8-3. 배포와 그 한계

정적 앱으로 GitHub Pages 에 배포한다.

```
https://hey-byeunya.github.io/already-got-it-guide-bot/        ← 이 챗봇 (고객용)
https://hey-byeunya.github.io/already-got-it-guide-bot/dev/    ← dev-bot (개발자용)
```

> ⚠️ **배포 주소에서 답변 생성은 되지 않는다.** 답을 만드는 것은 고객 컴퓨터의 Ollama인데, 배포 페이지는 HTTPS이고 Ollama는 HTTP라 브라우저가 그 요청을 막는다. `OLLAMA_ORIGINS`를 설정해도 막힌다 — CORS가 아니라 **사설망 접근**이라는 별개의 관문이고, Ollama는 그 헤더를 보내지 않는다.

숨기지 않고, 대신 **답변 생성만 빼고 나머지를 배포 주소에서 실제로 동작하게** 만든다.

| 단계 | 배포 주소에서 | 왜 되는가 |
|---|---|---|
| 질문을 벡터로 | ✅ | 브라우저 안에서 돈다 |
| 도움말 검색 | ✅ | 정적 파일 + 브라우저 계산 |
| 참고한 도움말 카드 · 원문 열기 | ✅ | 링크만 열면 된다 |
| 호출 전 검사 | ✅ | 프로그램이 한다 |
| 답변 생성 · 자동 판정 | ❌ | Ollama가 필요하다 |

즉 링크만 연 사람도 **"이 질문의 답은 이 도움말들에 있습니다"까지는 실제로 받는다.** 고객센터로서 이것도 유효한 응답이다. 완전한 답변을 보려면 저장소를 내려받아 직접 띄운다 — README에 `OLLAMA_ORIGINS` 설정과 실행 방법을 적는다.

## 9. dev-bot 에서 이어받은 것과 바꾼 것

| 무엇 | dev-bot | support-bot | 왜 |
|---|---|---|---|
| 자료 | 개발 문서 14청크 (PRD·SQL·rules) | **고객 도움말 18~22청크** | 고객이 출처를 열어 읽을 수 있어야 한다 |
| 답변 형식 | 자유 서술 + `[AG-004]` | **결론 → 절차 → 주의 + `[1]`** | 고객센터 답변의 모양 |
| 인용 판정 | 판정 모델 (실패 42건) | **프로그램** | 글자를 찾으면 끝나는 일이다 |
| 화면 | 검토 지표가 전면 | **고객 모드 / 검토 모드** | 주인공이 바뀌었다 |
| 없는 기능 질문 | "자료에 없습니다" | **"없습니다" (faq.md 근거)** | 없다는 사실도 답이다 |
| 검색·임베딩·게이트·부정문 | — | **그대로 이어받는다** | 측정으로 검증된 것을 다시 만들 이유가 없다 |
| 답변 엔진 | 로컬 Ollama | **그대로** | 외부 서비스를 늘리지 않는다 |

**이어받은 규칙 하나**: 부탁하는 자리(프롬프트)와 지키는 자리(프로그램)를 나눈다. dev-bot 이 여섯 실험으로 얻은 결론이고, 이 챗봇은 그것을 처음부터 구조로 갖는다.
