# 이미 있어 이용 안내 챗봇 — PRD

> **상태: 완성본 (H단계, 수용 기준 6/6 통과).** `[결정 필요]` 6곳을 모두 닫았다 — B에서 2곳, C에서 1곳, F에서 1곳, G에서 1곳, 그리고 제출 직전에 마지막 2곳. **빈칸은 없다.**
> 닫은 근거는 모두 실제로 돌려 본 측정이다. 정하지 못한 것을 정한 척하지 않았고, 정할 수 있게 된 것을 미루지도 않았다.
> 빈칸을 남긴 채 구현을 시작하면, 나중의 코드 선택이 제품 약속을 대신하게 된다.

## 0. 이 문서로 판단할 것

처음 보는 사람이 이 문서를 읽고 **무엇을 물을 수 있고 무엇을 기대하면 안 되는지** 알 수 있어야 한다. 그게 이 PRD의 합격 조건이다.

한 줄로 답하면 — **"이미 있어"의 공개 문서에 적힌 것은 물을 수 있고, 내 계정 안의 데이터는 물을 수 없다.**

---

## 1. 스스로에게 묻는 여덟 질문

| # | 질문 | 답 |
|---|---|---|
| 1 | 누구의 어떤 불편을 다루는가 | "이미 있어"를 처음 쓰는 사람이 화면 어디서 무엇을 하는지, 왜 카테고리가 필수인지 몰라 등록에서 막힌다. 답은 공개 문서에 있지만 다섯 파일에 흩어져 있어 찾기 어렵다 |
| 2 | 사용자가 끝내 할 수 있어야 하는가 | 질문한 뒤, 답의 근거가 된 문서 조각과 그 원문 주소를 열어 직접 확인한다 |
| 3 | 제품의 한 문장 목표는 | 공개 문서에 근거해 "이미 있어"의 이용 방법을 안내하고, 그 근거를 화면에 함께 드러낸다 |
| 4 | 이번 범위에서 하지 않을 일은 | 로그인, 개인 데이터 조회, 상태 변경 제안, 서버에서의 자료 수집 (3절) |
| 5 | 어떤 자료를 사실로 삼는가 | 공개 저장소의 문서 5개 (4절). 미리보기 화면은 B에서 뺐다 |
| 6 | 답하지 못할 때 어떤 행동을 하는가 | 범위 밖임을 밝히고, 관련 자료를 요청하거나 답할 수 없다고 안내한다 (5절) |
| 7 | 사용자가 성공을 어떻게 알아보는가 | 스트리밍으로 이어지는 답변 + 출처 칩(ID·섹션·검색 방법·점수) + 판정 배지가 한 화면에 함께 보인다 |
| 8 | 어떤 관찰로 수용 여부를 판정하는가 | 7절의 수용 기준 6개를 질문과 화면 상태로 하나씩 확인한다 |

## 1-1. 타겟 유저 — 누가 사용하는가

셋으로 나뉜다. **셋 다 "이 답을 믿어도 되나"를 스스로 판단해야 하는 사람**이라는 점이 같다.

| 누구 | 무엇을 묻는가 | 무엇을 기대하면 안 되는가 |
|---|---|---|
| **"이미 있어"를 처음 쓰는 사람** | "위시에 담아둔 걸 샀는데 어떻게 옮겨요?" 처럼 화면에서 무엇을 눌러야 하는지 | 내 계정에 무엇이 들어 있는지. 이 챗봇은 로그인하지 않는다 |
| **규칙을 확인하려는 사용자** | "카테고리는 꼭 넣어야 해요?" 처럼 입력이 왜 막히는지 | "그 값은 통과합니다"라는 판정. 규칙이 적힌 문장을 보여 줄 뿐이다 (5-3) |
| **이 챗봇을 검토하는 사람** | 답이 어느 문서 어느 대목에서 나왔는지 | 판정 배지가 답의 정확성을 증명해 준다는 것. 판정은 같은 2B 모델이 한다 (F) |

**로그인한 사용자를 대상으로 삼지 않는다.** 이 챗봇은 누구인지 몰라도 답할 수 있는 것만 다루고, 그것이 3절 비목표의 첫 줄이다.

세 번째(검토하는 사람)를 타겟에 넣은 이유가 있다. 이 챗봇은 답을 주는 것만큼 **근거를 열어 보이는 것**이 목적이라, 근거를 확인하려는 사람이 쓰기 어려우면 만든 뜻이 없다. 출처 칩·근거 모달·판정 배지가 그 사람을 위한 것이다.

## 2. 목표

- "이미 있어"의 공개 문서에 근거해 이용 방법을 안내한다.
- **자료에 근거해 만든 답변마다** 근거가 된 문서 조각과 원문 주소를 함께 보인다. (거부 답변은 예외 — 7절)
- 자료에 없는 질문에는 **답을 만들어 내지 않고 경계를 알린다.**

---

## 3. 비목표 — 이번 범위에서 약속하지 않는 것

비목표는 목표를 줄이는 사과가 아니라, **어떤 계약을 약속하지 않는지 미리 선언하는 안전장치**다.

| 하지 않는 것 | 이유 |
|---|---|
| 로그인 · 사용자 계정 | 이 챗봇은 누구인지 몰라도 답할 수 있는 것만 다룬다 |
| 개인 데이터 조회 ("내 있템 몇 개?") | 4강 설계에서 개인정보 열람은 챗봇이 단독 결정하지 않기로 정했다 |
| 값이 규칙에 맞는지 판정해 주기 | 판정에는 폼의 맥락이 필요하다. 문서 문장을 보여 주는 데까지만 한다 |
| 상태 변경 제안 (위시→있템 등) | 되돌릴 수 없는 동작이다. 사람이 앱 화면에서 직접 누른다 |
| 계정·비밀번호를 대신 조작하기 | 재설정 메일 발송, 약관 동의, 닉네임 변경을 대행하지 않는다. 화면 경로만 안내한다 |
| 서버에서 자료를 수집하기 | 서버가 없다. 자료는 미리 만들어 둔 파일이고, 검색과 생성은 사용자 브라우저와 그 컴퓨터의 Ollama가 한다 |
| 다국어 · 모바일 최적화 | 이번 범위 밖 |

> 위 셋(개인 데이터 조회 · 값 판정 · 상태 변경 제안)은 [4강 설계 패킷](https://github.com/hey-byeunya/my-service-agent/blob/main/design-packet.md)의 도구 2·3·4다. 설계에서 이미 "챗봇이 단독으로 결정하지 않는다"고 정한 것들이라, 이번에 빼는 것이 설계와 어긋나지 않는다. 이번 구현은 그 패킷의 **도구 1 `search_usage_guide` 하나**에 해당한다.

## 5. 자료 밖 질문 처리 기준

자료에 없는 질문은 **그럴듯하게 넓혀 답하지 않는다.** 자료 범위 밖임을 밝힌 뒤 둘 중 하나를 한다.

1. **관련 자료를 요청한다** — 답이 있을 만한 문서를 사용자가 알려 줄 수 있는 경우
2. **답할 수 없다고 안내한다** — 공개 자료에 없는 주제인 경우

> 이 기준은 **거절 횟수를 줄이려는 장치가 아니라, 사용자가 답변의 경계를 이해하게 하는 약속이다.**
> 그래서 정당한 거부를 실패로 세지 않고 `refusal:true`로 따로 센다. 거부가 줄어드는 것이 좋은 신호가 아니다 — 자료 밖 질문에 답을 지어내기 시작하면 거부는 줄어든다.

### 5-1. 세 경우

| 상황 | 행동 |
|---|---|
| 검색 결과가 비었다 | 자료에 없다고 말하고 멈춘다 |
| 개인 데이터·계정 조작을 요구한다 | 이 챗봇의 범위 밖임을 밝히고, 앱 화면 경로만 안내한다 |
| 근거는 있는데 약하다 (최고 유사도 0.55 미만) | 근거를 버리지 않는다. 약한 근거 경고를 띄우고 보수적으로 답한다 |

### 5-2. 판정이 실패했을 때

답변을 자동으로 판정하는 단계가 결과를 돌려주지 못할 수 있다(형식이 깨진 응답 등). 이때 **판정 배지 자리에 실패 표시만 남기고, 이미 만든 답변과 출처는 지우지 않는다.**

판정은 답변을 다시 읽게 돕는 보조 장치이지, 답변이 화면에 남을 조건이 아니다. 판정이 실패했다고 답변까지 지우면 사용자는 무엇이 잘못됐는지 볼 기회를 잃는다.

### 5-3. 문서를 보여 주는 것과 값을 판정하는 것의 경계

이 챗봇은 **값 판정을 하지 않는다**(3절). 그런데 "수량 0으로 등록되나요?" 같은 질문에 문서의 "수량은 1 이상" 문장을 보여 주면, 읽는 사람은 판정을 받았다고 느낀다.

경계를 이렇게 긋는다.

| 한다 | 하지 않는다 |
|---|---|
| 규칙이 적힌 문서 문장을 근거와 함께 보여 준다 | "그 값은 통과합니다 / 거부됩니다"라고 판정해 말한다 |
| "문서에는 이렇게 적혀 있습니다"로 시작한다 | 문서에 없는 조합을 미루어 판정한다 |

문서에 그 값에 대한 문장이 없으면 **추측해서 판정하지 않고 없다고 말한다.** 판정처럼 들리는 답이 가장 위험한 자리다 — 사용자는 확인했다고 믿고 넘어간다.

## 6. 기능 목록 — 각 항목이 사용자의 무엇을 돕는가

기능 이름만 적으면 왜 있는지 알 수 없다. **각 항목에 사용자의 판단을 돕는 이유를 붙인다.**

| 기능 | 사용자가 무엇을 판단하게 되는가 |
|---|---|
| 출처 칩 (ID · 섹션 · 검색 방법 · 점수) | 이 답을 믿을지, 원문을 열어 볼지 스스로 정한다 |
| 답변 안의 `[AG-0xx]` 인용 표시 | 답의 어느 문장이 어느 조각에서 나왔는지 짚는다 |
| 원문 주소 링크 | 챗봇의 말과 실제 문서를 직접 대조한다 |
| 약한 근거 경고 | 근거가 약한 답을 평소와 같은 자신감으로 읽지 않는다 |
| 판정 배지 (grounded · noHalluc · cited · refusal) | 답을 두 번째 시선으로 다시 읽는다 |
| 스트리밍 + 중지 버튼 | 답이 길어질 때 계속 기다릴지 끊을지 정한다 |
| 연결 상태 배너 | 페이지가 고장 난 것인지, 자기 컴퓨터에서 Ollama를 켜야 하는 것인지 구별한다 |
| 소개 화면의 사용 조건 | **쓰기 전에** 자기 환경이 조건을 갖췄는지 판단한다 |

---

## 6-1. 화면 구성

한 페이지짜리 앱이다. 화면을 나누지 않은 이유는, **질문이 입력된 순간부터 근거와 답변과 판정이 한자리에서 보여야** 하기 때문이다. 근거를 보러 다른 화면으로 가야 하면 대조하지 않게 된다.

> 이 표는 계획이 아니라 **만든 화면을 문서로 되돌린 것**이다. 초안 PRD에는 화면 구성이 없었고, 제출 기준과 대조하다 빠진 것을 발견해 실제 화면(`app/src/App.tsx`)을 읽어 채웠다.

| 영역 | 무엇을 보여 주는가 | 왜 필요한가 |
|---|---|---|
| 소개 | 사용 조건 4단계, 물을 수 있는 것/없는 것, HTTPS 주의 | **쓰기 전에** 자기 환경이 조건을 갖췄는지 판단 |
| 연결 상태 배너 | Ollama 연결 여부·모델 유무·재시도 버튼 | 페이지가 고장 난 것인지, 자기 컴퓨터를 손봐야 하는지 구별 |
| 진행률 | 모델 내려받기 바이트와 막대 (195MB) | 기다릴지 떠날지 판단. 없으면 멈춘 화면으로 보인다 |
| 질문 입력 | 보내기 · 생성 중지 · 임베딩 대조 · 피드백 내려받기 | 답이 길어질 때 끊을 수 있게. 누른 값을 `check_feedback.ts` 가 읽을 파일로 꺼낼 수 있게 |
| 단계 표시 | 벡터로 → 근거 찾는 중 → 답 만드는 중 → 판정 중 | 어디까지 갔는지 |
| 호출 전 검사 배너 | 막은 규칙 이름과 "모델을 부르지 않았습니다" | 왜 답이 안 나왔는지 (3절 비목표에 걸린 것) |
| 약한 근거 경고 | 최고 유사도와 함께 "평소만큼 믿지 마세요" | 근거가 약한 답을 같은 자신감으로 읽지 않게 |
| 답변 | 스트리밍으로 이어지는 본문 | |
| 출처 칩 | ID · 섹션 · 검색 방법 · 점수 | 믿을지, 원문을 열지 스스로 정한다 |
| 근거 모달 | 조각 **원문 전체** + 원문 링크 (bm25면 점수 해석 주의) | 화면을 떠나지 않고 원문과 대조 |
| 판정 배지 | grounded · noHalluc · cited · refusal · score + 평어 | 답을 두 번째 시선으로 다시 읽는다 |
| 사람 피드백 | 도움됨/아니요 + **자동 판정과 어긋나면 경고** | **판정 밖의 기준**을 하나 둔다. 판정은 답을 만든 것과 같은 모델이라 독립 심사가 아니다 |
| 피드백 기록 안내 | **의견 접수함이 아니라는 것**, 몇 건이 쌓였는지, 읽는 쪽이 `check_feedback.ts` 라는 것 | 무엇에 쓰이는 값인지 누르기 전에 알게. 새로고침하면 사라진다는 것도 |

**이건 사용자 의견을 모으는 창구가 아니다.** 서버가 없어(3절 비목표) 남이 누른 값은 개발자에게 오지 않는다. **판정이 맞았는지 재기 위한 자료**이고, 읽는 쪽은 `scripts/check_feedback.ts` 다. 실제로 이 고리에서 [OBS-003](docs/failures.md)이 나왔다 — 판정이 답의 환각(`AG-026`, 없는 ID)을 검증 없이 자기 근거로 되받은 새 유형이다.

**피드백은 판정을 받은 답에만 붙는다.** 호출 전 검사에 막힌 답과 오류가 난 답에는 버튼이 없다 — 대조할 자동 판정이 없기 때문이다.

**만들지 않은 화면**: 로그인, 대화 기록 보관, 설정 페이지. 로그인은 3절 비목표이고, 나머지 둘은 이번 범위 밖이다.

## 7. 수용 기준

### 어떤 답에 출처가 있어야 하는가

- 자료에 근거해 만든 **모든 답변**은 `[AG-0xx]` 인용을 포함한다.
- **거부 답변에는 인용이 없어도 된다.** 근거가 없어서 거부한 것이므로, 인용을 요구하면 없는 근거를 만들게 된다.

### 어떤 경우에 거부가 정당한가

아래 셋은 `refusal:true`가 **정답**이고 감점 대상이 아니다.

1. 검색 결과가 비었을 때
2. 개인 데이터·계정 조작을 요구할 때
3. 공개 자료 범위 밖 주제일 때

### 수용 기준 — 입력할 질문과 관찰할 화면 상태

| # | 입력할 질문 | 관찰할 화면 상태 |
|---|---|---|
| 1 | "위시에 담아둔 걸 샀는데 어떻게 옮겨요?" | 스트리밍 답변 안에 `[AG-0xx]` 인용이 보이고, 출처 칩에 섹션·검색 방법·점수가 표시된다 |
| 2 ✅ | "내일 날씨 어때?" | `refusal:true` 배지가 뜨고, 답변에 자료 밖 사실이 없다 — **F 에서 확인됨** |
| 3 ✅ | "제 있템이 몇 개예요?" | 개인 데이터는 범위 밖임을 밝히고, 근거 없이 수를 말하지 않는다 — **호출 전 검사로 통과.** 모델을 부르지 않으므로 수를 말할 방법이 없다 |
| 4 | (Ollama를 끈 상태로 접속한다) | 연결 실패 배너와 재시도 버튼이 보이고, 페이지 오류처럼 보이지 않는다 |
| 5 ✅ | "내일 날씨 어때?" (최고 유사도 **0.514**) | 약한 근거 경고가 뜨고, 답변이 보수적으로 바뀐다 — **임베딩에 접두어를 붙여 통과.** 화면에 「근거가 약합니다 — 0.514 로 0.55 미만」이 뜨고 프롬프트에 보수화 문구가 들어간다 |
| 6 | (배포 주소의 소개 화면을 연다) | 사용 조건 4단계가 README와 **같은 문장**으로 보인다 |

**5번은 한동안 검증할 수 없는 기준이었다.** C에서 재 보니 "내일 날씨 어때?" 같은 완전히 무관한 질문조차 0.584로 0.55를 넘었다. 약한 근거 경고가 켜지는 상황 자체가 발생하지 않았다.

기준을 지우지 않고 남겨 두었다 — 지우면 "약한 근거를 어떻게 다룰 것인가"라는 약속까지 사라진다. 그리고 **임베딩 방식을 바꿔 통과시켰다.**

EmbeddingGemma는 문서와 질문에 서로 다른 접두어를 붙여 쓰도록 만들어진 모델인데, 명세가 그것을 말하지 않아 붙이지 않고 있었다. 붙이자 "내일 날씨 어때?"가 **0.514**로 내려가 0.55 미만이 됐고, 근거 있는 질문 중 가장 낮은 것은 0.604라 **오탐 0건**이다. **명세의 0.55를 바꾸지 않고** 그 기준이 작동하게 만든 것이다.

혼자서는 안 됐다 — 접두어만으로는 두 무리의 틈이 −0.013으로 여전히 음수였다. 가장 높은 범위 밖 질문이 "제 있템이 지금 몇 개예요?"였는데, 그 질문은 이제 **호출 전 검사가 막아 검색에 도달하지 않는다.** 그것을 빼자 틈이 **+0.016**이 됐다. 수용 기준 3번을 고친 것이 5번을 함께 풀었다. 측정값은 [임베딩 비교](docs/vectorstore.md#수용-기준-5번을-푼-과정)에 있다.

3번은 4강 설계에서 정한 "개인정보 열람은 챗봇이 단독으로 결정하지 않는다"가 **화면까지 도착했는지** 보는 자리다. 문서에만 적혀 있고 UI에서 지켜지지 않으면 지킨 것이 아니다.

그런데 C의 측정은 3번도 어렵게 만들었다. "제 있템이 지금 몇 개예요?"의 top-1 점수가 **0.648**로, 근거 있는 질문들과 같은 띠에 있다. 점수로는 이 질문이 범위 밖이라는 신호가 전혀 나오지 않는다.

**그래서 프롬프트에서 빼고 호출 전 검사로 옮겼다.** 이제 이 질문은 모델에게 가지 않는다 — 검색도, 생성도, 판정도 하지 않고 프로그램이 즉시 막는다. 모델이 보지 못하는 질문에는 흔들릴 여지가 없다.

막는 범위는 3절이 비목표로 못 박은 셋뿐이다(개인 데이터 조회·계정 대행·상태 변경 대행). "자료에 없는 주제" 전체를 낱말로 막지는 않는다 — 그건 셀 수 있는 것이 아니고, 그 판단은 근거를 읽어야 나온다. 게이트는 셀 수 있는 것만 맡는다.

가장 위험한 것은 답할 수 있는 질문을 막는 것이라, 통과해야 할 질문 13개와 막아야 할 질문 8개로 시험한다(`node scripts/check_gate.ts`) — **오탐 0건, 미탐 0건.** 「어떻게·방법·되나요」처럼 방법을 묻는 문장은 막지 않는다.

### 걸려 있던 위험 — 그리고 실제로 일어난 일 (2026-08-28)

**B단계에서 이렇게 적었다**: 로컬 작업본에 `CLAUDE.md`를 주제별 파일로 쪼개는 변경이 커밋되지 않은 채 있고, 그것이 푸시되면 청크 일부는 원문에 없는 문장이 된다.

> ⚠️ 그때 브랜치 관계를 **반대로 적었다**. "로컬이 원격보다 7 커밋 앞섬"이라고 썼지만 실제는 그 반대였다 — 로컬 브랜치는 `main`이 아니라 `dev`였고, `dev`는 `origin/main`보다 **7 커밋 뒤에 있으면서** 1 커밋 앞서 있었다. `git rev-list --left-right --count`의 좌우를 뒤집어 읽은 것이다. 위험 자체는 실재했지만, 근거로 든 숫자의 방향이 틀렸다.

**그리고 실제로 푸시됐다.** `dev`를 `main`에 병합해 문서 분리가 공개됐고, 예상한 대로 청크 3개가 깨졌다.

| 청크 | 무슨 일이 있었나 |
|---|---|
| AG-005 · AG-012 | 본문이 `CLAUDE.md` → `docs/rules/data-access.md`로 옮겨졌다 |
| AG-007 | 본문이 `CLAUDE.md` → `docs/rules/fields.md`로 옮겨졌다 |

**본문 자체는 한 글자도 바뀌지 않았다.** 글자 수가 옮기기 전과 같다(267 · 321 · 260자). 파일과 제목 단계만 달라졌다. 그래서 고친 것은 청크의 `url`과 `section`뿐이고, `text`는 그대로다.

이 사고가 확인해 준 것이 하나 있다 — **재검토 조건 1번("그 청크의 본문이 원문에 아직 있는가")을 사람이 기억하는 대신 스크립트가 매번 검사하게 해 둔 것이 맞았다.** `scripts/build_chunks.py`가 원문을 새로 받아 대조하다가 세 청크에서 멈췄고, 무엇이 어디로 갔는지 바로 보였다. 눈으로 확인했다면 링크가 열린다는 이유로 넘어갔을 것이다.

## 10. PRD 검토 결과

과제가 준 검토 프롬프트를 그대로 적용했다. 구현을 시작하기 전에 이 문서의 모순과 빠진 기준을 먼저 찾는 것이 목적이다.

### ① 목표와 비목표가 충돌하거나 모호한 지점 — 질문으로

**Q1. "답변마다 근거를 함께 보인다"(2절)는 거부 답변에도 적용되는가?**
7절은 "거부 답변에는 인용이 없어도 된다"고 적었다. 2절의 "답변마다"와 7절의 예외가 서로 다른 말을 한다. 둘 중 하나를 고쳐야 한다.

**Q2. "값이 규칙에 맞는지 판정해 주기"를 하지 않는다면(3절), "수량 0으로 등록되나요?"에는 어떻게 답하는가?**
문서에 "수량은 1 이상"이라고 적혀 있으므로 그 문장을 보여 줄 수는 있다. 그런데 그것을 읽은 사용자는 판정을 받았다고 느낀다. **문서 문장을 보여 주는 것과 값을 판정하는 것의 경계가 답변 안에서 흐려진다.** 이 경계를 어디에 그을지 5절에 없다.

**Q3. `/preview` 화면을 자료로 삼는 것(4절)은 "서버에서 자료를 수집하기"를 하지 않는다는 비목표(3절)와 충돌하지 않는가?**
화면을 자료로 쓰려면 누군가 그 화면을 읽어 문장으로 옮겨야 한다. 그 작업 자체가 수집이다. 문서 파일과 달리 화면에는 "원문 문장"이 없어서, 옮겨 적은 문장은 원문 대조가 불가능하다.

### ② 공개 자료만으로 검증할 수 없는 수용 기준

**수용 기준 5 — 검증 불가 (지금은).**
"근거가 약한 질문(최고 유사도 0.55 미만)"이라고 적었지만, **어떤 질문이 0.55 미만인지 벡터스토어를 만들기 전에는 알 수 없다.** 지금 이 칸은 관찰할 화면 상태는 있으나 입력할 질문이 없다. C단계 이후에 실제 질문을 특정해 채워야 한다.

**수용 기준 3 — 근거의 출처가 자료 밖이다.**
"제 있템이 몇 개예요?"에 "범위 밖"이라고 답하려면 그 규칙을 어딘가에서 읽어야 한다. 그런데 **그 규칙은 이 PRD에만 있고 청크에는 없다.** 검색 결과가 비었을 때 모델은 무엇을 근거로 "범위 밖"이라고 말하는가? 프롬프트에 넣으면 되지만, 그건 "자료에 근거한 답"이 아니라 **지시문에 근거한 답**이다. 두 종류의 답이 화면에서 구별되는지 정해야 한다.

### ③ 도메인 밖 · 근거 부족 · 판정 실패의 처리 기준

앞 둘은 5절에 있다. **판정 실패는 빠져 있다.**

| 상황 | 지금 문서 | 제안 |
|---|---|---|
| 도메인 밖 | 5절에 있음 | 유지 |
| 근거 부족 | 5절에 있음 (0.55 미만 보수화) | 유지 |
| **판정 실패** | **없음** | 판정이 JSON을 돌려주지 못하면 판정 배지 자리에 실패 표시만 남기고, **이미 만든 답변과 출처는 지우지 않는다.** 판정은 답변을 읽는 보조 장치이지 답변의 조건이 아니다 |

점검했다. 이 문서에 적힌 수치는 셋뿐이고 모두 출처가 있다 — 유사도 임계 0.55(과제 명세), 임베딩 다운로드 약 200MB(강의 자료), 로컬이 원격보다 7 커밋 앞섬(`git rev-list`로 직접 확인). 청크 개수·루브릭 목표값처럼 **아직 재지 않은 수치는 넣지 않고 `[결정 필요]`로 남겼다.**
