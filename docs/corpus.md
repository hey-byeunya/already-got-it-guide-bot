# B단계 — 자료 수집 기록

공개 원문에서 **연속된 구간을 그대로 잘라** 청크 14개를 만들었다. 요약하거나 다시 쓰지 않았다 — 사용자가 출처를 열었을 때 같은 문장이 그 자리에 있어야 하기 때문이다.

생성: `python3 scripts/build_chunks.py` → `data/chunks.json`
스크립트가 원문을 매번 새로 내려받으므로, 자료가 바뀌면 다시 돌려 어긋난 곳을 찾을 수 있다.

## 공개 URL이 없어 넣지 않은 자료

로그인이나 권한이 필요하거나, 공개 주소가 없는 것들이다. 내용이 좋아도 넣지 않았다.

| 자료 | 왜 뺐나 |
|---|---|
| `docs/rules/fields.md` · `auth.md` · `session.md` · `data-access.md` | 로컬 작업본에만 있고 원격에 없다 (404) |
| `components/CLAUDE.md` | 같음 (404) |
| 실제 서비스 화면 (`/`, `/wishlist`, `/used`, `/items/new`, `/wishlist/new`) | 로그인해야 열린다 |
| `/preview` · `/preview/wishlist` | 공개지만 **화면에는 대조할 원문 문장이 없다.** 옮겨 적으면 그 문장의 출처를 확인할 방법이 사라진다 → PRD `[결정 필요] 2`를 이 이유로 닫았다 |

원격 `CLAUDE.md`가 규칙 분리 이전의 통합본이라, 로컬 `docs/rules/*`의 내용이 그 안에 그대로 있다. 그래서 빠뜨린 사실은 없다 — 다만 **로컬 변경이 푸시되면 AG-005·AG-007·AG-012의 본문이 원문에서 사라진다.**

## 사람이 원문으로 확인할 항목

1. **AG-005 · AG-007 · AG-012에 개발자용 내용이 섞여 있다.** 파일 경로(`lib/owned-item-sort.ts`), 함수 이름(`mark_wishlist_purchased`, `deriveUsedUpAt`) 같은 것들이다. 주제는 하나지만, 이 문장이 사용자 답변에 그대로 인용되면 읽을 수 없는 답이 된다. 잘라내지 않은 이유는 **잘라내면 원문과 다른 문장이 되어 출처 대조가 깨지기** 때문이다. E단계에서 실제로 인용되는지 관찰하고, 문제가 되면 G의 실험 후보로 삼는다.

2. **AG-014는 SQL 코드다.** 넣은 이유는 `status`·`quantity` 같은 정확한 낱말을 낱말 기반 검색(BM25)이 잡게 하려는 것이다. 실제로 도움이 되는지, 아니면 답변에 코드가 튀어나오기만 하는지는 C의 검색 스팟체크에서 확인한다.

3. **AG-011(Won't)은 시점 정보다.** "알림 없음", "바코드 스캔 없음"은 지금 기준이다. 기능이 하나라도 추가되면 **가장 먼저 틀리는 청크**다. 자료 갱신 검토 시 이것부터 본다.

4. **PRD 머리말의 버전(v1.5)과 최종 수정일(2026-07-23)은 청크에 넣지 않았다.** 날짜를 물으면 답할 근거가 없다. 이건 빠뜨린 게 아니라 뺀 것이다 — 문서 버전은 이용 방법이 아니고, 넣으면 갱신될 때마다 틀린 답을 하게 된다.

5. **AG-001은 468자, AG-002는 450자, AG-014는 688자로 다른 청크보다 길다.** 길다고 나쁜 건 아니지만, 긴 청크는 검색에서 여러 질문에 두루 걸리면서 정작 정확한 답을 밀어낼 수 있다. C의 스팟체크에서 이 셋이 엉뚱한 질문의 top-1로 올라오는지 본다.
