# 실패한 답 — 어느 단계가 원인이었나

```bash
node scripts/collect_failures.ts   # data/failures.json 생성
```

두 갈래로 모은다.

| 파일 | 무엇 | 어떻게 모았나 |
|---|---|---|
| `data/failures.json` | 측정 기록 108건에서 규칙으로 뽑은 실패 | 스크립트 |
| `data/observed-failures.json` | 실제로 써 보다 발견한 사례 | 사람이 원문과 대조 |

**두 파일을 섞지 않는다.** 앞은 고정 질문 9개 × 3회의 측정이라, 손으로 관찰한 다른 질문을 끼워 넣으면 측정 구조가 깨진다.

원자료 **108건**(4세팅 × 9문항 × 3회)에서 실패를 뽑아 원인 단계로 나눴다. 답을 지우지 않고 다 남겨 두었기 때문에 셀 수 있었다.

**분류는 사람이 정한 규칙으로 한다.** 자동 분류를 모델에게 맡기면 또 하나의 못 믿을 판정이 생긴다 — F 에서 판정이 기계로 확인 가능한 항목에서도 틀리는 것을 봤다.

## 원인 단계별 건수

| 단계 | 유형 | 건수 | 무엇이 실패인가 |
|---|---|---|---|
| **판정** | 배지와 점수가 다른 말 | **55** | `noHalluc=false`(지어낸 사실 있음)인데 80점 이상을 함께 줬다 |
| **판정** | `cited` 가 실제와 다름 | **42** | 답변에 `[AG-…]` 표기가 있는데 없다고 하거나 그 반대 |
| **생성** | 출처 표기 없이 답함 | 19 | 자료에 근거해 답해야 할 문항인데 `[AG-…]` 가 하나도 없다 |
| **생성** | 근거가 있는데 못 찾음 | 17 | 근거 10~13개를 넘겼는데 판정이 `grounded=false` |
| **거부** | 자료 밖인데 답해 버림 | 4 | 무근거 문항에 거부하지 않았다 (전부 Q9 "월 구독료") |
| 판정 | 형식이 깨진 응답 | 0 | 이 원자료 범위에서는 없었다 (F 의 별도 실행에서 1건 있었다) |

## 읽는 법 — 세는 것과 원인은 다르다

**건수가 많은 순서가 심각한 순서가 아니다.** 위 다섯 중 **위 둘은 판정의 실패**이고, 판정 자체가 못 미덥다는 것은 G 의 두 실험이 이미 보였다. 즉 55건과 42건은 "답이 나빴다"가 아니라 **"자를 믿을 수 없다"**는 뜻에 가깝다.

그래서 아래처럼 나눠 읽는다.

### 판정이 원인인 것 (97건)

**배지와 점수가 다른 말 (55건).** 명세는 `score` 가 `grounded`·`noHalluc`·`cited` 를 반영해야 한다고 했는데, 지어낸 사실이 있다고 판정하면서 90점을 주는 일이 절반 넘게 일어났다. **화면에서 점수만 보면 안 되는 이유**라서, 판정 배지 옆에 그 사실을 적어 두었다.

**`cited` 가 실제와 다름 (42건).** `cited` 는 답변에 `[AG-…]` 가 있는지 세면 끝나는 항목이다. 정규식 한 줄로 확인되는 것을 모델에게 물었고, 그래서 틀렸다. G 에서 프롬프트를 두 방향으로 고쳐 봤지만 **어느 쪽으로 건드려도 나아지지 않았다.**

> **처방은 프롬프트가 아니다.** `cited` 를 모델에게 묻지 말고 프로그램이 세서 채우면 이 42건은 0이 된다. 「실행하지 않은 것」에 적어 두었다 — 지금 바꾸면 기준 행이 무효가 되어 실험 결과를 읽을 수 없게 되기 때문이다.

### 생성이 원인인 것 (36건)

**출처 표기 없이 답함 (19건).** 프롬프트가 `[ID]` 표시를 요구하는데 지키지 않았다. 짧은 답에서 먼저 사라지는 경향이 있다 — G 의 지표 5 가 잡으려던 것이다.

**근거가 있는데 못 찾음 (17건).** 이게 가장 아픈 자리다. E 에서 확인한 대표 사례가 이렇다.

> 질문 "위시에 담아둔 걸 샀는데 어떻게 있템으로 옮겨요?" 에 `AG-004` 가 **첫 번째 근거**로 들어갔고 그 안에 답이 그대로 있다 — "샀어요 · 있템으로"를 누르면 있템으로 원자적 전환. 그런데 모델은 "문서에 적혀 있지 않습니다" 라고 답했다.

**검색이 아니라 생성의 실패다.** `show_prompt.ts` 로 확인하니 프롬프트는 정확했다. 다만 **검색이 근거를 10~13개나 넘긴 것**이 배경이다 — 답이 뭉치에 묻힌다. 청크가 14개뿐이라 "상위 10 + 미중복 5" 가 사실상 전체를 덮기 때문이고, 그 수치는 훨씬 큰 코퍼스를 전제한 설계다.

### 검색·청크가 배경인 것 (별도 관찰)

건수로 세어지지 않지만 위 실패들의 배경이다.

| 무엇 | 어디서 봤나 |
|---|---|
| 코드 표기와 자연어를 못 이음 | "수량을 0으로 등록할 수 있나요?" → `AG-007`(`owned_items.quantity` 규칙)이 3위로 밀림 |
| 같은 주제를 두 청크가 나눠 가짐 | `AG-003`(D-day 배지) ↔ `AG-012`(계산 시점) — 배지 쪽이 자주 이김 |
| BM25 가 범위 밖 질문에 근거를 만듦 | "파이썬으로 웹 크롤링" 에 `AG-001` 이 정규화 점수 **1.00** 으로 붙음 |

마지막 것이 특히 문제라, 근거 모달에 "`bm25` 의 1.00은 «관련 있다»가 아니라 «이 검색 안에서 1등»"이라는 설명을 붙였다.

### 거부가 원인인 것 (4건)

전부 **Q9 "이 앱 월 구독료가 얼마예요?"** 다. 자료에 요금 이야기가 없으니 거부해야 하는데 답해 버렸다.

호출 전 검사는 이 질문을 막지 않는다 — 개인 데이터가 아니기 때문이다. "자료에 없는 주제" 전체를 낱말로 막으려 하면 오탐이 생긴다. **이 자리는 여전히 모델의 판단에 달려 있다.**

## 실제 사용 중 관찰한 것 — `data/observed-failures.json`

위 108건은 스크립트가 고정 질문 9개를 돌린 **측정 기록**이다. 그와 별도로, 화면에서 직접 써 보다 발견한 것을 따로 모은다. **두 파일을 섞지 않는다** — 루브릭 원자료에 손으로 관찰한 다른 질문을 끼워 넣으면 세팅당 9문항 × 3회라는 측정 구조가 깨진다.

### OBS-001 — "위시에 넣은 것 옮기기" (2026-08-31)

답은 매끄럽게 791자가 나왔고 `[AG-005]`·`[AG-008]`을 인용했다. 판정은 **85점**을 줬다. 그런데 원문과 대조하니 **오류가 다섯 가지** 있었다.

| # | 심각도 | 유형 | 모델이 쓴 것 | 원문 |
|---|---|---|---|---|
| 1 | **높음** | 부정을 뒤집음 | "삭제 + 생성 조합에 의해 처리되며, 부분 반영 상태가 생길 수 있음을 인정" | "두 번 호출해 조합**하지 않는다** — 부분 반영이 생길 수 있기 **때문**" |
| 2 | **높음** | 규칙을 정반대로 | "이름과 카테고리가 **있는 항목만** 생성합니다" | "카테고리가 없으면 NULL로 그대로 넘어가며, **전환 자체가 막혀서는 안 된다**" |
| 3 | 중간 | 없는 UI 문구 | "「위로 보유테인」으로 이동하는 버튼" | "「샀어요 · 있템으로」를 누르면" |
| 4 | 낮음 | 자리표시자 출력 | "해당 `ID [AG-XXX]` 를 기준으로" | `[AG-XXX]`는 실제 ID가 아니다 |
| 5 | 낮음 | 없는 낱말 | "보유테인", "원천 처리" | 원문에 없는 조어 |

**1번은 같은 답 안에서 자기모순이다.** 바로 윗줄에서는 "API로 두 번 호출하지 않습니다"라고 **맞게** 썼는데, 다음 줄에서 뒤집었다.

**2번이 사용자에게 가장 해롭다.** 이 답을 믿으면 "카테고리 없는 위시는 못 옮기는구나"라고 오해한다. 원문은 정확히 그 반대를 말한다.

**3번은 검색 탓이 아니다.** `AG-004`("샀어요 · 있템으로")가 **top-1 근거**로 들어가 있었는데도 버튼 이름을 지어냈다.

### 판정은 어땠나

| | |
|---|---|
| **맞은 것** | `noHalluc=false`를 켰다 — 지어낸 것이 있다는 신호는 맞았다 |
| **틀린 것** | 점수 **85**를 함께 줬다. 배지와 점수가 다른 말을 한다 |
| **틀린 것** | 평어가 "**핵심 메커니즘이 명확히 전달**되므로 높은 점수를 받았습니다"라고 했는데, 그 핵심 메커니즘이 바로 뒤집힌 부분이다 |
| **틀린 것** | `grounded=true` — 근거를 읽기는 했으나 정반대로 읽었다 |

### 어느 단계가 원인인가

**생성이다.** 검색은 필요한 조각(`AG-004`·`AG-005`)을 모두 넘겼다.

배경이 둘 있다. 근거 11개가 한꺼번에 들어가 답이 뭉치에 묻히고, **원문에 "~하지 않는다", "막혀서는 안 된다" 같은 부정문이 많은데 2B 모델이 그것을 자주 뒤집는다.**

**판정이 못 잡은 이유도 같다.** 판정도 같은 2B 모델이라 같은 부정문을 같은 방식으로 잘못 읽는다. 답을 만든 모델이 답을 채점하는 구조의 한계다.

### 이 사례가 확인해 주는 것

화면에 넣은 두 문구가 정확히 이 상황을 위한 것이다.

> 이 답이 **읽기에 매끄러운 것**과 **자료에 근거한 것**은 다릅니다.
>
> 점수가 높아도 「지어낸 사실 없음」이 꺼져 있을 수 있습니다. 배지를 하나씩 보세요.

**답만 읽으면 매끄러워서 넘어간다.** 출처 칩을 열어 원문과 대조해야 잡힌다. 이 사례는 사람이 그렇게 해서 찾았다.

### 새 실험 후보

| 후보 | 축 | 왜 |
|---|---|---|
| 부정문이 든 청크를 답할 때 원문을 그대로 인용하게 요구 | 프롬프트 | 다시 쓰는 과정에서 부정이 뒤집힌다. 옮겨 적게 하면 줄어들 수 있다 `[추정]` |
| 근거 개수를 줄인다 (D 후보 6번과 같은 자리) | 검색 | 11개가 한꺼번에 들어간다 |

## 각 단계로 되짚는 법

`data/failures.json` 의 사례마다 **세팅·회차·문항**이 적혀 있다. 원자료에서 그 답의 전문을 찾을 수 있다.

```bash
python3 -c "
import json
rows = json.load(open('data/rubric/baseline.json'))
r = [x for x in rows if x['run']==1 and x['id']=='Q9'][0]
print(r['answer'])"
```

## 지우지 않은 것

점수가 낮은 답, 판정이 틀린 답, 예상과 반대로 나온 실험 결과를 하나도 지우지 않았다. **다음 수정이 무엇을 보존해야 하는지는 실패한 답이 알려 준다** — 위 표가 그 답에서 나왔다.
