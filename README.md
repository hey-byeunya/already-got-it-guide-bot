# 이미 있어 이용 안내 챗봇

**[이미 있어](https://already-got-it.vercel.app)**의 공개 문서에 근거해 이용 방법을 안내하는 챗봇입니다. 답할 때마다 **어느 문서의 어느 대목을 근거로 삼았는지** 함께 보여 줍니다.

서버가 답을 만들지 않습니다. 이 페이지를 연 **당신 컴퓨터의 Ollama**가 직접 답을 만듭니다. 그래서 아래 사용 조건이 필요합니다.

## 쓰기 전에 확인할 것

1. 이 페이지를 열고, 이 챗봇이 다루는 자료와 물을 수 있는 질문을 읽습니다.
2. 내 컴퓨터에서 Ollama를 실행하고 `qwen3.5:2b`를 준비합니다.
3. 첫 방문에는 임베딩 모델 다운로드(약 200MB)가 있습니다. 끝날 때까지 기다립니다.
4. `OLLAMA_ORIGINS`에 이 페이지 주소를 허용한 뒤, 안내된 질문과 자료 밖 질문을 각각 입력해 봅니다.

```bash
# macOS
launchctl setenv OLLAMA_ORIGINS "https://hey-byeunya.github.io"
# 설정 뒤 Ollama를 재시작합니다
```

Chrome과 Edge를 권장합니다. Safari에서는 Ollama 연결과 임베딩이 불안정할 수 있습니다.

> ⚠️ 배포 주소는 HTTPS이고 Ollama는 HTTP라, 브라우저가 그 요청을 막습니다. `OLLAMA_ORIGINS`를 설정해도 막힙니다. 지금 확실히 쓰는 방법은 저장소를 내려받아 `npm run dev`로 직접 띄우는 것입니다.

## 물을 수 있는 것과 없는 것

| 물을 수 있다 | 물을 수 없다 |
|---|---|
| 위시를 있템으로 옮기는 방법 | 내 있템이 몇 개인지 |
| 카테고리·수량·상태 입력 규칙 | 내 계정·비밀번호 관련 조작 |
| 쓴템 탭의 뜻과 되돌리는 방법 | 이 앱에 없는 기능 (자료에 없으면 없다고 답합니다) |
| D-day 배지 네 단계의 의미 | 오늘 날씨 같은 앱 밖 이야기 |

자료에 없는 질문에는 **답을 지어내지 않고 자료 범위 밖이라고 알립니다.** 이건 거절을 줄이려는 게 아니라, 어디까지 믿어도 되는지 알려 드리기 위한 약속입니다.

## 설계 결정 요약

**청크를 요약하지 않고 원문에서 그대로 잘랐습니다.** 정리해서 쓰면 읽기는 좋아지는데, 사용자가 출처를 열었을 때 **그 문장이 거기 없습니다.** 그러면 출처를 보여 주는 의미가 사라집니다. 그래서 만드는 스크립트가 매번 "잘라낸 문장이 원문에 아직 있는지"를 대조하고, 어긋나면 멈춥니다. 실제로 자료 문서가 쪼개졌을 때 이 검사가 청크 세 개를 잡아냈습니다 — 링크는 그대로 열렸기 때문에 눈으로는 못 찾았을 문제입니다.

**문서 벡터와 질문 벡터를 같은 경로로 만들었습니다.** 문서 쪽은 미리 만들어 두고 질문 쪽은 브라우저가 그때그때 만드는데, 둘이 다른 방식이면 숫자는 나오지만 비교할 자리를 잃습니다. 같은 모델 파일·같은 실행 방식·같은 계산으로 맞추고, 같은 문장을 양쪽에서 만들어 견줘 **1.000000**을 확인했습니다. 화면의 「임베딩 대조」 버튼이 언제든 다시 잽니다.

**만들면서는 검색·프롬프트를 고치지 않았습니다.** 결과가 마음에 안 들어도 그 자리에서 손대면, 나중에 무엇이 무엇을 바꿨는지 알 수 없습니다. 바꾸고 싶은 것은 모두 적어 두었다가 실험 단계에서 하나씩 바꿔 재고, **흔들림보다 큰 차이만 변화로 읽었습니다.**

## 실험 결과

고정 질문 아홉 개(Q1~Q9)를 세팅마다 **세 번씩** 돌렸습니다. 자세한 기록은 [docs/rubric.md](docs/rubric.md), 답변 원문 **108건**(4세팅 × 9문항 × 3회)은 [data/rubric/](data/rubric)에, 실패를 원인별로 나눈 것은 [docs/failures.md](docs/failures.md)에 있습니다.

### 왜 세 번씩 돌렸나

같은 질문에 답도 판정도 매번 달라지기 때문입니다. 한 번 돌린 결과를 비교하면, 달라진 게 바꾼 것 때문인지 그냥 매번 다른 것인지 알 수 없습니다. 그래서 세팅마다 세 번 돌려 **얼마나 흔들리는지 폭을 먼저 재고, 그 폭보다 큰 차이만 변화로 읽었습니다.**

### 고정 질문

| 종류 | 질문 |
|---|---|
| 정상 (한 문서로 답함) | Q1 위시에 담아둔 걸 샀는데 어떻게 있템으로 옮겨요? · Q2 다 쓴 물건은 어디서 볼 수 있어요? · Q3 회원가입할 때 닉네임은 몇 글자까지예요? |
| 경계 (두 문서를 이어야 함) | Q4 카테고리를 비워서 등록하면 위시에서 옮겨올 때도 비어 있나요? · Q5 수량을 0으로 등록할 수 있나요? · Q6 어제 본 D-day랑 숫자가 다른데 왜 그래요? |
| 무근거 (자료에 없음) | Q7 내일 날씨 어때? · Q8 제 있템이 지금 몇 개예요? · Q9 이 앱 월 구독료가 얼마예요? |

### 무엇을 쟀나

| 지표 | 무엇을 보는가 | 목표 | 지금 |
|---|---|---|---|
| 출처를 인용한 답 | 여섯 문항 중 출처를 밝힌 답의 수 | 6/6 | 5.0 |
| 범위 밖 질문의 거부 | 세 문항 중 "자료에 없다"고 답한 수 | 3/3 | 2.3 |
| 근거성 | 답이 자료에서 나온 비율 | 1.00 | 0.83 |
| **판정을 믿을 수 있는가** | 판정이 "출처를 밝혔다"고 한 것이 실제와 맞은 비율 | 0.90 | **0.74** |
| 짧은 답의 근거 유지 | 답이 짧아져도 출처 표시가 남는가 | 숫자 목표 없음 | 431자 |

네 번째는 과제가 준 목록에 없는 항목인데 넣었습니다. 다른 지표가 모두 자동 판정을 근거로 삼는데, **그 판정 자체가 얼마나 맞는지 재지 않으면 나머지를 읽을 수 없기** 때문입니다.

### 실험 네 개 — 둘은 되돌리고 둘은 채택했습니다

| 실험 | 바꾼 것 | 결과 | 결정 |
|---|---|---|---|
| 생성 온도 고정 | 답을 만들 때 온도를 0으로 | 흔들림은 줄었지만 답이 짧아지며 출처 표시가 줄었고, **판정 정확도가 0.74 → 0.48** | **되돌림** |
| 출처 표기 형식 통일 | 자료에 붙는 이름표를 `[AG-004 \| 섹션]` → `[AG-004]` 로 | 표기가 100% 의도한 형식으로 바뀌었는데도 **판정 정확도가 0.74 → 0.59** | **되돌림** |
| **호출 전 검사** | 개인 데이터 질문을 모델에게 보내기 전에 프로그램이 막음 | 집계 숫자는 거의 그대로. 대신 **흔들릴 수 없게 됨** | **채택** |
| **임베딩 표시 붙이기** | 문서와 질문에 모델이 원래 요구하는 표시를 붙임 | 자료 안팎 질문의 점수가 갈려 **약한 근거 경고가 처음으로 켜짐** | **채택** |

**되돌린 둘과 채택한 둘은 판단 근거가 다릅니다.** 되돌린 둘은 숫자가 나빠져서 되돌렸습니다. 채택한 둘은 **숫자가 좋아져서가 아니라** — 하나는 흔들리지 않게 됐고, 하나는 그동안 검증할 수 없던 기준을 검증 가능하게 만들었습니다. 채택 근거를 숫자로 적을 수 없다는 것도 그대로 적어 둡니다.

**첫 번째에서 배운 것**: 온도 하나만 바꿨다고 생각했는데, 온도가 답 길이를 줄이고, 길이가 출처 표시를 줄이고, 그게 판정을 틀리게 만들었습니다. "한 번에 하나만 바꾼다"는 건 **넣는 것을 하나만 바꾼다**는 뜻이지, 결과가 한 곳에만 나타난다는 뜻이 아니었습니다.

**두 번째에서 배운 것**: 제 예상이 틀렸습니다. 판정이 출처를 못 알아보는 건 형식 때문이라고 봤는데, 형식을 정확히 맞춘 뒤 **오히려 더 자주 틀렸습니다.**

### 되돌린 두 실험이 함께 말하는 것

어느 쪽으로 건드려도 판정 정확도가 떨어졌습니다. 남는 결론은 하나입니다 — **문제는 문구가 아니라, 답을 만든 것과 같은 작은 모델에게 판정을 맡긴 구조 자체입니다.**

그래서 다음에 할 일은 문구 고치기가 아닙니다. **"출처를 밝혔는가"는 모델에게 묻지 않고 프로그램이 직접 세면 됩니다.** 글자를 찾으면 끝나는 일을 모델에게 물어볼 이유가 없었습니다.

## 배포 주소

**https://hey-byeunya.github.io/already-got-it-guide-bot/**

> ⚠️ **주소는 열리지만 답은 만들어지지 않습니다.** 배포 주소는 HTTPS이고 Ollama는 HTTP라, 브라우저가 그 요청을 막습니다. `OLLAMA_ORIGINS`를 설정해도 막힙니다.
>
> 배포하고 직접 따라가 보다 찾았고, **실제 Chrome에서도 다시 확인했습니다**(`Failed to fetch`). 브라우저 도구 문제가 아닙니다.
>
> Ollama가 요청 허용 헤더는 제대로 보냅니다 — `curl`로 확인하면 `Access-Control-Allow-Origin`이 이 주소로 정확히 돌아옵니다. 그런데 HTTPS 페이지가 `http://localhost`에 닿으려면 **관문을 하나 더**(사설망 접근) 지나야 하고, Ollama는 그 헤더(`Access-Control-Allow-Private-Network`)를 보내지 않습니다.
>
> 배포 주소에서 볼 수 있는 것: 소개 화면, 사용 조건, 연결 실패 안내와 재시도. 답변·출처·판정까지 보시려면 아래처럼 직접 띄우세요.
>
> 질문을 보내면 **모델을 받기 전에 연결부터 확인해** 몇 초 안에 안내를 보여 줍니다. 195MB를 받은 뒤에 실패하지 않습니다.

```bash
git clone https://github.com/hey-byeunya/already-got-it-guide-bot.git
cd already-got-it-guide-bot/app && npm install && npm run dev
# http://localhost:5173 — 페이지와 Ollama가 같은 http 라서 막히지 않습니다
```

## 사용 조건

숨기지 않고 그대로 적습니다.

1. **당신 컴퓨터에서 Ollama가 실행 중이어야 합니다** — `qwen3.5:2b` 준비 (`ollama pull qwen3.5:2b`)
2. **첫 방문에 임베딩 모델을 약 195MB 받습니다** — 실측값입니다. 받는 동안 진행률과 막대가 보이고, 한 번 받으면 브라우저에 저장돼 다음부터는 기다리지 않습니다
3. **`OLLAMA_ORIGINS` 설정이 필요합니다** — 다만 위 ⚠️ 때문에 배포 주소에서는 그것만으로 충분하지 않습니다

|---|---|---|---|
| 자료에 근거해 답해야 할 6문항 중 출처를 밝힌 답 | 6/6 | 4~6개 | 미달 |

## 실행하지 않은 것과 이유

**판정을 프로그램으로 옮기지 않았습니다.** "출처를 밝혔는가"는 글자를 찾으면 끝나는 일인데 모델에게 물었고, 그래서 자주 틀렸습니다 — 실패 108건 중 **42건이 이것**입니다([실패 정리](docs/failures.md)).

**답이 원문의 부정을 뒤집는 것을 막지 못했습니다.** 실제로 써 보다 찾았습니다 — "위시에 넣은 것 옮기기"에 매끄러운 791자가 나왔는데, 원문의 "~하지 **않는다**"를 "~한다"로 뒤집은 곳이 두 군데 있었습니다. 자동 판정은 「지어냈을 수 있음」을 켜면서도 **85점**을 함께 줬습니다. 이런 답은 **출처 칩을 열어 원문과 대조해야만** 잡힙니다 — 그래서 화면에 "매끄러운 것과 근거 있는 것은 다르다"를 적어 두었습니다. 사례 전문은 [`data/observed-failures.json`](data/observed-failures.json)에 있습니다. 고치는 방법은 실험으로 분명해졌지만, 그러면 기준으로 삼은 값이 흔들려 실험 결과를 읽을 수 없게 됩니다. **다음 회차에 바꾸고, 바꾸기 전후를 같은 질문으로 다시 재는 것**이 순서입니다.

**다른 답변 엔진을 붙이지 않았습니다.** 로컬 Ollama 하나만 씁니다. 외부 서비스를 늘리지 않기로 한 범위와 맞습니다.

**"자료에 없는 주제" 전체를 프로그램이 막게 하지는 않았습니다.** "이 앱 월 구독료가 얼마예요?" 같은 질문이 남습니다(실패 4건). 개인 데이터가 아니라 낱말로 셀 수 없고, 억지로 막으면 답할 수 있는 질문까지 막힙니다.

*(개인 데이터 질문 차단과 약한 근거 경고는 이 목록에 있었으나 해결했습니다 — 아래 두 절을 보세요.)*

## 호출 전 검사 — 모델에게 부탁하지 않고 프로그램이 막습니다

"제 있템이 몇 개예요?" 같은 질문은 **모델에게 가지 않습니다.** 검색도, 답 만들기도, 판정도 하지 않고 프로그램이 즉시 막습니다.

지시문에 "개인 데이터를 조회하지 않는다"고 적어 두었을 때는 여섯 번 중 한 번 지켜지지 않았습니다. 검색 점수도 신호를 주지 못했습니다 — 이 질문의 점수가 답할 수 있는 질문들과 같은 띠에 있습니다. 그래서 부탁하는 자리에서 빼내 **프로그램이 지키는 자리로 옮겼습니다.**

막는 것은 셋뿐입니다 — 내 데이터 조회, 계정·비밀번호 대행, 데이터 대신 바꾸기. 이 셋은 처음부터 "하지 않는다"고 정해 둔 것들입니다.

**"자료에 없는 주제" 전체를 막지는 않습니다.** 그건 낱말로 셀 수 있는 것이 아니고, 그 판단은 근거를 읽어야 나옵니다. 프로그램은 셀 수 있는 것만 맡습니다.

가장 위험한 건 **답할 수 있는 질문을 막아 버리는 것**입니다. 그래서 통과해야 할 질문 13개와 막아야 할 질문 8개로 매번 시험합니다 — **잘못 막은 것 0건, 놓친 것 0건.** "비밀번호를 잊었는데 어떻게 재설정해요?"처럼 아슬아슬한 것도 통과합니다. **방법을 묻는 문장은 막지 않기** 때문입니다.

막혔을 때는 화면에 무엇이 막았는지 보입니다 — 「호출 전 검사에서 멈췄습니다 — 개인 데이터 조회」.

## 약한 근거 경고 — 두 가지를 함께 고쳐야 켜졌습니다

근거가 약할 때 "이 답을 평소만큼 믿지 마세요"라고 알리는 장치가 있는데, **한 번도 켜지지 않았습니다.** 켜지는 기준이 0.55인데 "내일 날씨 어때?" 같은 완전히 무관한 질문조차 0.584가 나왔기 때문입니다. 자료에 있는 질문과 없는 질문의 점수가 겹쳐서, 어떤 값을 잡아도 둘을 가를 수 없었습니다.

**두 가지를 고치자 갈렸습니다.**

첫째, 쓰고 있는 임베딩 모델은 원래 문서와 질문에 **서로 다른 표시를 붙여** 쓰도록 만들어졌는데, 그걸 안 붙이고 있었습니다. 붙였습니다.

둘째, 겹침을 만든 건 "제 있템이 지금 몇 개예요?"였습니다. 자료에 있는 낱말로만 되어 있어 점수가 높게 나옵니다. 그런데 **이 질문은 이제 호출 전 검사가 막습니다** — 검색에 도달하지 않으니 애초에 셈에서 빠져야 할 질문이었습니다.

결과: "내일 날씨 어때?"가 **0.514**로 내려가 경고가 켜집니다. 답할 수 있는 질문 중 가장 낮은 것은 0.604라 **잘못 켜지는 경우는 0건**입니다.

**기준값 0.55는 바꾸지 않았습니다.** 숫자를 데이터에 맞춰 옮길 수도 있었지만, 그러면 그 숫자가 왜 그 값인지 설명할 근거가 질문 열몇 개뿐이 됩니다.

> ⚠️ 두 무리 사이 간격이 **0.016으로 좁습니다.** 질문 13개로 잰 값이라 새 질문이 오면 다시 겹칠 수 있습니다. "지금 이 자료와 이 질문들에서 작동한다"는 뜻이지 보편적인 값이 아닙니다.

**여기서 배운 것**: 두 변경이 각각으로는 안 되는데 함께 작동했습니다. "한 번에 하나만 바꾼다"는 원인을 분리하려는 규칙이지, 변경끼리 영향을 주고받지 않는다는 뜻이 아니었습니다. 하나씩 재 본 뒤에는 합쳐서 다시 재야 합니다.
