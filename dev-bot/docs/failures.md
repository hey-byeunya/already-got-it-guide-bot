# 실패한 답 — 어느 단계가 원인이었나

```bash
node scripts/collect_failures.ts   # data/failures.json 생성
```

세 갈래로 모은다.

| 파일 | 무엇 | 어떻게 모았나 |
|---|---|---|
| `data/failures.json` | 측정 기록 108건에서 규칙으로 뽑은 실패 | 스크립트 |
| `data/observed-failures.json` | 실제로 써 보다 발견한 사례 | 사람이 화면에서 찾아 원문과 대조 |
| `data/feedback/*.json` | 화면에서 「도움됨 / 아니요」를 누른 기록 | 파일로 꺼내 `check_feedback.ts` 가 셈 |

**세 파일을 섞지 않는다.** 첫째는 고정 질문 9개 × 3회의 측정이라, 손으로 관찰한 다른 질문을 끼워 넣으면 측정 구조가 깨진다. 둘째와 셋째는 둘 다 실제 사용에서 나오지만 **찾은 경로가 다르다** — 하나는 사람이 화면을 보다, 하나는 눌린 값을 세다 나온다. 경로가 다르면 무엇을 놓치는지도 다르다.

원자료 **108건**(4세팅 × 9문항 × 3회)에서 실패를 뽑아 원인 단계로 나눴다. 답을 지우지 않고 다 남겨 두었기 때문에 셀 수 있었다.

**분류는 사람이 정한 규칙으로 한다.** 자동 분류를 모델에게 맡기면 또 하나의 못 믿을 판정이 생긴다 — F 에서 판정이 기계로 확인 가능한 항목에서도 틀리는 것을 봤다.

## 원인 단계별 건수

| 단계 | 유형 | 건수 | 무엇이 실패인가 |
|---|---|---|---|
| **판정** | 배지와 점수가 다른 말 | **55** | `noHalluc=false`(지어낸 사실 있음)인데 80점 이상을 함께 줬다 |
| **판정** | `cited` 가 실제와 다름 | **42** | 답변에 `[AG-…]` 표기가 있는데 없다고 하거나 그 반대 |
| **생성** | 출처 표기 없이 답함 | 19 | 자료에 근거해 답해야 할 문항인데 `[AG-…]` 가 하나도 없다 |
| **생성** | 근거가 있는데 못 찾음 | 17 | 근거 10~13개를 넘겼는데 판정이 `grounded=false` |
| **거부** | 자료 밖인데 답해 버림 | 4 | 무근거 문항에 거부하지 않았다 (전부 Q9 "월 구독료") |
| 판정 | 형식이 깨진 응답 | 0 | 이 원자료 범위에서는 없었다 (F 의 별도 실행에서 1건 있었다) |

## 읽는 법 — 세는 것과 원인은 다르다

**건수가 많은 순서가 심각한 순서가 아니다.** 위 다섯 중 **위 둘은 판정의 실패**이고, 판정 자체가 못 미덥다는 것은 G 의 두 실험이 이미 보였다. 즉 55건과 42건은 "답이 나빴다"가 아니라 **"자를 믿을 수 없다"**는 뜻에 가깝다.

그래서 아래처럼 나눠 읽는다.

### 판정이 원인인 것 (97건)

**배지와 점수가 다른 말 (55건).** 명세는 `score` 가 `grounded`·`noHalluc`·`cited` 를 반영해야 한다고 했는데, 지어낸 사실이 있다고 판정하면서 90점을 주는 일이 절반 넘게 일어났다. **화면에서 점수만 보면 안 되는 이유**라서, 판정 배지 옆에 그 사실을 적어 두었다.

**`cited` 가 실제와 다름 (42건).** `cited` 는 답변에 `[AG-…]` 가 있는지 세면 끝나는 항목이다. 정규식 한 줄로 확인되는 것을 모델에게 물었고, 그래서 틀렸다. G 에서 프롬프트를 두 방향으로 고쳐 봤지만 **어느 쪽으로 건드려도 나아지지 않았다.**

> **처방은 프롬프트가 아니다.** `cited` 를 모델에게 묻지 말고 프로그램이 세서 채우면 이 42건은 0이 된다. 「실행하지 않은 것」에 적어 두었다 — 지금 바꾸면 기준 행이 무효가 되어 실험 결과를 읽을 수 없게 되기 때문이다.
>
> ⚠️ **다만 정규식만으로는 부족하다.** OBS-003 에서 `[AG-]` 표기 3개가 전부 **없는 ID** 인 답을 봤다. 표기만 세면 그 답이 「출처를 밝힘」으로 잡힌다. **표기가 있는지가 아니라 그 ID 가 실제로 넘긴 근거 안에 있는지를 대조해야 한다.** 프로그램이 할 수 있는 일이라는 점은 그대로다.

### 생성이 원인인 것 (36건)

**출처 표기 없이 답함 (19건).** 프롬프트가 `[ID]` 표시를 요구하는데 지키지 않았다. 짧은 답에서 먼저 사라지는 경향이 있다 — G 의 지표 5 가 잡으려던 것이다.

**근거가 있는데 못 찾음 (17건).** 이게 가장 아픈 자리다. E 에서 확인한 대표 사례가 이렇다.

> 질문 "위시에 담아둔 걸 샀는데 어떻게 있템으로 옮겨요?" 에 `AG-004` 가 **첫 번째 근거**로 들어갔고 그 안에 답이 그대로 있다 — "샀어요 · 있템으로"를 누르면 있템으로 원자적 전환. 그런데 모델은 "문서에 적혀 있지 않습니다" 라고 답했다.

**검색이 아니라 생성의 실패다.** `show_prompt.ts` 로 확인하니 프롬프트는 정확했다. 다만 **검색이 근거를 10~13개나 넘긴 것**이 배경이다 — 답이 뭉치에 묻힌다. 청크가 14개뿐이라 "상위 10 + 미중복 5" 가 사실상 전체를 덮기 때문이고, 그 수치는 훨씬 큰 코퍼스를 전제한 설계다.

### 검색·청크가 배경인 것 (별도 관찰)

건수로 세어지지 않지만 위 실패들의 배경이다.

| 무엇 | 어디서 봤나 |
|---|---|
| 코드 표기와 자연어를 못 이음 | "수량을 0으로 등록할 수 있나요?" → `AG-007`(`owned_items.quantity` 규칙)이 3위로 밀림 |
| 같은 주제를 두 청크가 나눠 가짐 | `AG-003`(D-day 배지) ↔ `AG-012`(계산 시점) — 배지 쪽이 자주 이김 |
| BM25 가 범위 밖 질문에 근거를 만듦 | "파이썬으로 웹 크롤링" 에 `AG-001` 이 정규화 점수 **1.00** 으로 붙음 |

마지막 것이 특히 문제라, 근거 모달에 "`bm25` 의 1.00은 «관련 있다»가 아니라 «이 검색 안에서 1등»"이라는 설명을 붙였다.

### 거부가 원인인 것 (4건)

전부 **Q9 "이 앱 월 구독료가 얼마예요?"** 다. 자료에 요금 이야기가 없으니 거부해야 하는데 답해 버렸다.

호출 전 검사는 이 질문을 막지 않는다 — 개인 데이터가 아니기 때문이다. "자료에 없는 주제" 전체를 낱말로 막으려 하면 오탐이 생긴다. **이 자리는 여전히 모델의 판단에 달려 있다.**

## 실제 사용 중 관찰한 것 — `data/observed-failures.json`

위 108건은 스크립트가 고정 질문 9개를 돌린 **측정 기록**이다. 그와 별도로, 화면에서 직접 써 보다 발견한 것을 따로 모은다. **두 파일을 섞지 않는다** — 루브릭 원자료에 손으로 관찰한 다른 질문을 끼워 넣으면 세팅당 9문항 × 3회라는 측정 구조가 깨진다.

### OBS-001 — "위시에 넣은 것 옮기기" (2026-08-31)

답은 매끄럽게 791자가 나왔고 `[AG-005]`·`[AG-008]`을 인용했다. 판정은 **85점**을 줬다. 그런데 원문과 대조하니 **오류가 다섯 가지** 있었다.

| # | 심각도 | 유형 | 모델이 쓴 것 | 원문 |
|---|---|---|---|---|
| 1 | **높음** | 부정을 뒤집음 | "삭제 + 생성 조합에 의해 처리되며, 부분 반영 상태가 생길 수 있음을 인정" | "두 번 호출해 조합**하지 않는다** — 부분 반영이 생길 수 있기 **때문**" |
| 2 | **높음** | 규칙을 정반대로 | "이름과 카테고리가 **있는 항목만** 생성합니다" | "카테고리가 없으면 NULL로 그대로 넘어가며, **전환 자체가 막혀서는 안 된다**" |
| 3 | 중간 | 없는 UI 문구 | "「위로 보유테인」으로 이동하는 버튼" | "「샀어요 · 있템으로」를 누르면" |
| 4 | 낮음 | 자리표시자 출력 | "해당 `ID [AG-XXX]` 를 기준으로" | `[AG-XXX]`는 실제 ID가 아니다 |
| 5 | 낮음 | 없는 낱말 | "보유테인", "원천 처리" | 원문에 없는 조어 |

**1번은 같은 답 안에서 자기모순이다.** 바로 윗줄에서는 "API로 두 번 호출하지 않습니다"라고 **맞게** 썼는데, 다음 줄에서 뒤집었다.

**2번이 사용자에게 가장 해롭다.** 이 답을 믿으면 "카테고리 없는 위시는 못 옮기는구나"라고 오해한다. 원문은 정확히 그 반대를 말한다.

**3번은 검색 탓이 아니다.** `AG-004`("샀어요 · 있템으로")가 **top-1 근거**로 들어가 있었는데도 버튼 이름을 지어냈다.

### 판정은 어땠나

| | |
|---|---|
| **맞은 것** | `noHalluc=false`를 켰다 — 지어낸 것이 있다는 신호는 맞았다 |
| **틀린 것** | 점수 **85**를 함께 줬다. 배지와 점수가 다른 말을 한다 |
| **틀린 것** | 평어가 "**핵심 메커니즘이 명확히 전달**되므로 높은 점수를 받았습니다"라고 했는데, 그 핵심 메커니즘이 바로 뒤집힌 부분이다 |
| **틀린 것** | `grounded=true` — 근거를 읽기는 했으나 정반대로 읽었다 |

### 어느 단계가 원인인가

**생성이다.** 검색은 필요한 조각(`AG-004`·`AG-005`)을 모두 넘겼다.

배경이 둘 있다. 근거 11개가 한꺼번에 들어가 답이 뭉치에 묻히고, **원문에 "~하지 않는다", "막혀서는 안 된다" 같은 부정문이 많은데 2B 모델이 그것을 자주 뒤집는다.**

**판정이 못 잡은 이유도 같다.** 판정도 같은 2B 모델이라 같은 부정문을 같은 방식으로 잘못 읽는다. 답을 만든 모델이 답을 채점하는 구조의 한계다.

### 이 사례가 확인해 주는 것

화면에 넣은 두 문구가 정확히 이 상황을 위한 것이다.

> 이 답이 **읽기에 매끄러운 것**과 **자료에 근거한 것**은 다릅니다.
>
> 점수가 높아도 「지어낸 사실 없음」이 꺼져 있을 수 있습니다. 배지를 하나씩 보세요.

**답만 읽으면 매끄러워서 넘어간다.** 출처 칩을 열어 원문과 대조해야 잡힌다. 이 사례는 사람이 그렇게 해서 찾았다.

### OBS-002 — "위시 옮기기" (2026-08-31)

답변 자리가 빈 채로 **「Error: Session mismatch」**만 떴다. 출처 칩도 판정 배지도 없다.

**이건 위 표에 들어갈 자리가 없다.** 청크·검색·프롬프트·판정·거부 어느 단계도 아니다. 답이 틀린 것이 아니라 **답이 아예 만들어지지 않았고**, 원인이 RAG 파이프라인이 아니라 화면 코드에 있다. 그래서 원인 단계별 건수에 더하지 않고 여기에만 적는다.

질문 때문이 아니다. **같은 질문을 한 번만 보내면 정상으로 답한다.**

#### 무엇이 원인이었나

**임베딩 계산이 두 번 겹쳐 돌았다.** ONNX Runtime 의 WASM 모듈은 한 번에 한 번의 추론만 받는다. 안에 "지금 돌고 있음" 표시가 하나뿐이고, 시작할 때 켜고 끝날 때 끈다.

```js
if (n.Fb) throw Error("Session already started");   // 두 번째 호출
let h = n.Fb = {...};
let y = await s(...l);
if (n.Fb !== h) throw Error("Session mismatch");     // 첫 번째 호출
finally { n.Fb = null }                              // ← 두 번째가 여기서 꺼 버린다
```

두 번째 호출이 `Session already started` 를 던지면서 표시를 꺼 버리고, 먼저 돌던 첫 번째가 돌아와 자기 표시가 사라진 것을 보고 `Session mismatch` 를 던진다. **즉 `Session mismatch` 를 받은 쪽이 먼저 시작한 호출이다** — 남의 사고에 휘말린 쪽이 실패한다.

#### 왜 겹쳤나 — 구멍이 둘

| # | 어디 | 무엇이 문제인가 |
|---|---|---|
| 1 | `App.tsx` — `disabled={busy}` | React 가 다시 그린 **뒤에야** 걸린다. 같은 순간에 들어온 두 번째 클릭은 아직 열려 있는 버튼을 누른다. 연타 직후 `button.disabled` 가 `false` 인 것을 실측했다 |
| 2 | `App.tsx` — `runParityCheck` | 이 함수도 `embed()` 를 부르는데 `setStage` 를 한 번도 부르지 않았다. 도는 내내 `busy` 가 `false` 라 「보내기」가 계속 눌린다. `try/catch` 도 없어 실패가 콘솔로만 샜다 |

`ask()` 첫 줄의 `abort.current?.abort()` 도 막지 못한다. `AbortSignal` 은 `fetch` 를 끊지, 이미 WASM 안에서 돌고 있는 `session.run` 은 끊지 못한다.

#### 재현

| 무엇을 | 화면 | 콘솔 |
|---|---|---|
| 한 번만 보내기 | 정상 답변 + 부정문 경고 | 없음 |
| 「임베딩 대조」 → 「보내기」 | `Session already started` | `Session mismatch` (uncaught) |
| **「보내기」 연속 두 번** | **`Session mismatch`** | `Session mismatch` (uncaught) |

세 번째가 신고된 화면과 같다.

#### 겸해서 드러난 것

`String(e)` 가 그대로 화면에 나왔다. `Session mismatch` 를 읽은 사용자가 할 수 있는 일이 없다. **`TypeError: Failed to fetch` 를 `cannotReach()` 로 고쳤을 때 같은 결함이 다른 자리에 남아 있던 것이다** — 그때 한 자리만 고쳤다.

#### 고친 것과 고친 뒤

| 어디 | 무엇 |
|---|---|
| `app/src/lib/embed.ts` | `session.run` 을 직렬 큐로 감쌌다. 겹쳐 들어온 호출은 실패시키지 않고 **줄을 선다** |
| `App.tsx` — `runParityCheck` | `setStage` 로 잠그고 `try/catch/finally` 를 붙였다 |
| `App.tsx` — `unexpected(e, what)` | `String(e)` 대체. 할 일을 먼저 쓰고 라이브러리 원문은 아래 줄에 남긴다 |

| 무엇을 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 「보내기」 3연타 | `Session mismatch` | 정상 답변 418자, 오류 없음 |
| 「임베딩 대조」 → 「보내기」 | `Session already started` | 보내기 잠김, 대조 **1.000000** |
| 대조 도중 실패 | 화면엔 아무것도, 콘솔로만 샘 | 화면에 문구, 콘솔 깨끗 |

큐를 고른 이유는 **부르는 곳이 몇 군데든 한 곳에서 막히기 때문**이다. 화면의 `disabled` 는 React 가 다시 그려 준다는 약속에 기댄 것이라 샌다.

#### 이 사례가 확인해 주는 것

지금까지 이 프로젝트는 **"프롬프트로 시킨 것은 실패하고 프로그램으로 옮긴 것만 성공했다"**로 적어 왔다(온도·표기·부정문 인용은 실패, 호출 전 검사는 성공). 이번 사례는 **상대가 모델이 아니어도 같았다**는 것을 보탠다. 버튼 잠금도 결국 "다시 그려 주면 걸린다"는 약속이고, 약속인 한 샌다. 자원을 쥔 자리에서 줄을 세우자 막혔다.

**부탁하는 자리와 지키는 자리를 나눈다는 원칙은 모델에만 적용되는 것이 아니다.**

### OBS-003 — 판정이 없는 근거를 재인용했다 (2026-08-31)

**찾은 경로가 앞의 둘과 다르다.** 화면을 보다 눈에 걸린 것이 아니라, 「피드백 내려받기」로 꺼낸 기록 **1건**을 `check_feedback.ts` 로 세고 원문과 대조하다 나왔다.

질문은 **"위시를 있템으로 옆기려면 어떻게 하나요?"** (오타는 실제 입력 그대로다.)

#### 답이 한 일 (547자)

| # | 무엇 | 실제 |
|---|---|---|
| 1 | **없는 ID 세 개를 만들어 냄** — `[AG-026]`, `[AG-17]`, `[AG-28]` | 청크는 `AG-001`~`AG-014`, **14개뿐**이다 |
| 2 | 실재하는 ID 에 다른 청크의 내용을 붙임 | 답이 `AG-013` 에서 인용했다는 "Won't (오늘은 일부러 뺄 것)" 은 `AG-011` 의 내용이다. `AG-013` 은 「6. 규칙 / 제약」 |
| 3 | 질문과 무관한 답 | 「샀어요 · 있템으로」가 든 `AG-004` 가 **top-1(0.712)** 로 들어갔는데 쓰지 않았다 |
| 4 | 없는 사실을 지어냄 | "현재 시각(2026년 8월) 기준으로 '손님이던' 것으로 간주된" — 원문에 없는 이야기다 |

3번은 OBS-001 과 같은 자리다. **검색이 정답 청크를 1위로 넘겼는데 생성이 쓰지 않았다.**

#### 판정이 한 일

| | |
|---|---|
| **`noHalluc=true`** | 위 네 가지가 다 있는데 「지어낸 것 없음」을 켰다 |
| **평어가 없는 ID 를 재인용** | "`AG-013` 의 제약 조건과 **`AG-026`** 의 위시리스트 관리 기능을 통해…" — `AG-026` 은 없다. **판정이 답의 환각을 검증 없이 자기 근거로 삼았다** |
| `cited=false` | 답에 `[AG-]` 표기가 3개 있다. 위 42건과 같은 유형 |
| `grounded=false` · 45점 | 결론만 보면 나쁜 답이라고 맞게 봤다 — 다만 **이유가 틀렸다** |

#### 사람은 「도움됨」을 눌렀다

**사람도 틀렸다.** `check_feedback.ts` 는 "갈렸다고 판정이 틀린 것은 아니다, 사람도 틀린다"고 적어 두었는데, **첫 기록이 정확히 그 경우였다.** 갈린 건은 원문과 대조할 후보이지 결론이 아니라는 것을, 표본 1건이 바로 보여 줬다.

#### 왜 새 유형인가

위 원인 표의 판정 실패 두 유형 — 배지↔점수가 다른 말(55건), `cited` 불일치(42건) — 어디에도 안 들어간다. 이건 **판정이 답의 환각을 확인 없이 근거로 되받은 것**이다. 답과 판정이 같은 `qwen3.5:2b` 라서, 판정에게는 그 ID 가 진짜인지 확인할 방법이 없었다. **판정을 독립 심사로 쓸 수 없다는 것의 가장 선명한 형태다.**

#### 검색은 어땠나 — `hits=14`

**청크 14개 중 14개가 근거로 들어갔다.** 「코사인 상위 10 + 미중복 BM25 5」는 훨씬 큰 코퍼스를 전제한 값인데, 14개짜리 코퍼스에서는 **전체를 덮는다.**

「근거가 있는데 못 찾음 17건」의 배경으로 "검색이 10~13개나 넘긴다"고 적어 두었던 것의 극단값이고, 여기서 처음 숫자로 확인됐다. 즉 이 프로젝트는 **검색이 아무것도 걸러내지 않는 상태에서 나머지를 재 왔다.** 검색을 실험 축으로 한 번도 건드리지 않은 것(D 후보 6번)이 여기서 값을 치른다.

#### 원자료

`data/feedback/feedback-2026-08-31_1211.json` — 대조 결과는 `data/feedback-result.json`.

`observed-failures.json` 에 넣지 않았다. 그 파일은 사람이 화면에서 찾은 것을 모은 것이고, 이건 눌린 값을 세다 나왔다. **경로가 다르면 섞지 않는다** (맨 위 표).
